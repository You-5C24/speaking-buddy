# 05 · 待验证问题

写代码之前或第一天就要实测的 5 件事。前 3 条是阻塞项，不通就得改方案。

---

## 1. 🔴 opus 转码后飞书客户端能不能正常显示时长

**为什么重要**：`duration` 填错会导致进度条错位，甚至发送失败。这是整条出链路唯一不确定的地方。

**怎么测**：

```bash
# 造一段 5 秒语音
say -v Samantha "Hi there, what can I get started for you?" -o t.aiff
ffmpeg -i t.aiff -c:a libopus -b:a 24k -ar 16000 -ac 1 t.opus
ffprobe -v error -show_entries format=duration -of csv=p=0 t.opus
# 然后把 duration 按毫秒填进上传和发送
```

**看什么**：
- 气泡上显示的秒数对不对
- 能不能正常播放
- iOS / Android / 桌面端是否一致（桌面端最容易出问题）

**如果不行**：试 `-ar 48000`（飞书客户端原生录制可能是 48k）、或者用 `-frame_duration 20`、或者换 `libopus` 的 `application=voip` 预设。

## 2. 🔴 资源下载接口的稳定性与耗时

`GET /open-apis/im/v1/messages/{message_id}/resources/{file_key}?type=file`

**为什么重要**：这是入链路的第一跳，超时或失败整个体验就断了。

**看什么**：
- 20 秒语音的实际字节数（估算 50–80KB）
- 下载耗时 p50 / p90
- 连续请求 10 次有没有限速（飞书的频率限制是按接口的）

**注意**：`type` 必须传 `file`。传 `image` 是常见错误，拿不到语音。

## 3. 🔴 ASR 对「非母语英语」的实际识别质量

**为什么重要**：整个复盘建立在转录上。如果 ASR 把 `I very like` 听成 `I really like`，你不仅纠不到错，还会误判。

**怎么测**：录 5 段自己的真实口语（带口音、带停顿、带填充词），跑一遍。

**看什么**：
- **词级置信度分布**。非母语用户的低置信词集中在哪？是虚词还是实词？如果低置信全是虚词，这个信号就没用。
- ASR 会不会「语法纠错」（有些引擎默认会把 `I very like` 自动改成 `I really like`）。**必须关掉这个功能**，否则你的语法纠错模块全部失效。
- 词级时间戳的精度（够不够算停顿）

候选：Whisper（自建，可控，有 word timestamp）、Azure STT、讯飞、Deepgram。

> **这条是失败成本最高的**。如果 ASR 会自动纠错，整个「发现错误」的链路就废了，得换引擎。

## 4. 🟡 复盘文档里能不能嵌入可播放音频

**为什么重要**：「你的原声 vs 标准音」是复盘里最有效的部分。如果不能嵌，效果打折。

**测法**（按优先级）：

1. 飞书文档能不能插入云盘音频文件并内联播放
2. 如果不行，退到「云盘附件 + 链接」
3. 再不行，把对比语音单独发成一条消息，文档里只放文字
4. 极端情况：用妙记（但要考虑成本）

**如果都不行**：接受它。文档里放 `turns/003/user.opus` 这样的路径，需要时手动听 —— 自己用，可以接受。

---

## 5. 🟡 飞书事件的重推与乱序

**为什么重要**：重推会导致重复回复（用户看到两条一模一样的语音）。乱序会导致对话错位。

**怎么测**：
- 连续快速发 3 条语音，看事件到达顺序和 `event_id` 有没有重复
- 故意让处理函数慢 15 秒，看飞书是否重推
- 断网重连后，看有没有补推积压事件

**预期**：飞书会重推。所以 `event_id` 去重是必须的，不是可选的。

## 第一天的验收标准

跑通这一条，后面就都是工程量：

> 我在飞书里发一条语音「I very like this coffee」，
> bot 在 5 秒内用语音回我一句带 `really like` 的自然回复，
> 并且把 `very like → really like` 记进了当轮的 `flags`。
