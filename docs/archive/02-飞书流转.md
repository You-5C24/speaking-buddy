# 02 · 飞书流转

一次完整练习的生命周期：**用户输入 → bot 接收 → bot 输出 → 结束判定 → 复盘 → 跟读**。

---

## 0. 全局前提

| 项 | 值 |
|---|---|
| 会话形态 | 单聊（`chat_type = p2p`） |
| 消息类型 | 进：`audio`（主）+ `text`（`/end` 等命令）· 出：`audio`（主）+ `interactive` 卡片 + `text`（兜底） |
| 接入方式 | WS 长连接（`@larksuiteoapi/node-sdk`，同 agent-os） |
| 单条语音上限 | 5 分钟（飞书客户端限制） |
| 单次练习 | 5–10 分钟，8–12 轮 |
| 延迟目标 | p50 ≤ 4s，p90 ≤ 8s（首句话开始播） |

### 需要申请的权限

| scope | 用途 |
|---|---|
| `im:message` | 收消息、读群/会话信息 |
| `im:message:send_as_bot` | 以机器人身份发消息 |
| `im:resource` | 下载语音资源（**最容易漏**） |
| `im:chat` | 取会话 basic info |
| `im:message.reaction:write` | 收到语音后回一个 emoji 当 ack（见 §2.3） |
| `docx:document` + `drive:drive` | 写复盘文档 |
| `bitable:app`（可选） | 指标落多维表格 |

订阅事件：`im.message.receive_v1`、卡片回调 `card.action.trigger`。

> 语音消息的 content 是 `{"file_key":"...","duration":3000}`，**没有下载 URL**，必须二次调资源接口。`duration` 单位毫秒，是飞书给你的；发语音时得你自己用 ffprobe 算好填上去。

## 1. 全链路时序

```
用户                                    飞书                    speaking-buddy
 │                                       │                           │
 │ ① 按住说话，发语音                      │                           │
 │──────────────────────────────────────>│                           │
 │                                       │ ② im.message.receive_v1   │
 │                                       │──────────────────────────>│
 │                                       │                           │ ③ 去重 + 入队
 │ ④ 消息上出现 emoji 表情                 │                           │    （立即 ack，不阻塞）
 │<──────────────────────────────────────│<──────────────────────────│
 │                                       │                           │ ④ 下载 opus
 │                                       │<──────────────────────────│    GET resources?type=file
 │                                       │──────────────────────────>│
 │                                       │                           │ ⑤ ffmpeg → 16k wav
 │                                       │                           │ ⑥ ASR + 词级时间戳
 │                                       │                           │ ⑦ 算韵律指标
 │                                       │                           │ ⑧ 状态机路由
 │                                       │                           │ ⑨ LLM 出新一句(JSON)
 │                                       │                           │ ⑩ TTS → opus + ffprobe
 │                                       │ ⑪ 上传 files(file_type=opus)│
 │                                       │<──────────────────────────│
 │                                       │──────────────────────────>│ file_key
 │                                       │ ⑫ message.create          │
 │ ⑬ 语音气泡                          │<──────────────────────────│    msg_type=audio
 │<──────────────────────────────────────│                           │
```

### 延迟预算（单轮）

| 阶段 | 目标 | 备注 |
|---|---|---|
| 事件推送 → 入队 | < 100ms | 必须马上 ack，飞书会重推 |
| 下载 opus | 150–300ms | 20s 语音约 40–80KB |
| ffmpeg 转码 | 80–150ms | 用 `-threads 1` 避免抢占 |
| ASR | 400–1200ms | 依赖供应商；批式比流式简单 |
| LLM 首 token | 300–800ms | **只取完整短回复，不做流式输出**（见下） |
| TTS 合成 | 300–900ms | 回复短（≤ 30 词）时最快 |
| ffmpeg → opus | 50–100ms | |
| 上传 + 发送 | 200–400ms | 两次 API 往返 |
| **合计** | **1.5–4s** | 加上网络抖动 |

> **为什么不做流式**：飞书的语音消息必须整段文件上传才能发，没法边生成边播。所以「流式」在这个渠道上没有收益。真正能省时间的是**让回复短** —— 1–3 句，30 词以内，既降延迟又符合可理解输入原则。

## 2. bot 接收

### 2.1 事件字段映射

```ts
// im.message.receive_v1 → IncomingVoice
{
  eventId:      evt.header.event_id,          // 去重键
  messageId:    evt.message.message_id,
  chatId:       evt.message.chat_id,
  chatType:     evt.message.chat_type,        // 'p2p'
  msgType:      evt.message.message_type,     // 'audio' | 'text'
  fileKey:      JSON.parse(content).file_key, // 仅 audio
  durationMs:   JSON.parse(content).duration,
  senderOpenId: evt.sender.sender_id.open_id,
  createTime:   evt.message.create_time
}
```

### 2.2 三条硬规则

1. **先 ack 再干活**。事件处理函数里只做「去重 + 入队 + 加 reaction」然后立即返回。所有下载/转码/推理都在队列 worker 里跑。飞书对超时事件会重推，重推会导致重复回复。
2. **按 `event_id` 去重**，落一份最近 500 条的 `seen-events.json`（或 Redis），重启不丢。
3. **按 `chat_id` 串行化**。同一个会话同一时刻只能有一个 turn 在跑。

### 2.3 「正在思考」的反馈

飞书 bot 没有 typing indicator。用 **reaction** 代替：

```
POST /open-apis/im/v1/messages/{message_id}/reactions
{ "reaction_type": { "emoji_type": "OnIt" } }
```

用户发完语音，1 秒内在自己那条消息上看到 👀，就知道被收到了。回复发出后可以撤掉或换成 ✅。

这一个小动作能把「等待 4 秒」的体感从「卡了」变成「在处理」。

### 2.4 并发消息的淘汰策略

用户可能连发两条语音。不要排队分别回复（会变成话痨），而是：

```
新语音到达 → 如果当前 turn 还在 THINKING：
  标记当前 turn 为 superseded
  把新旧两段音频按时间顺序拼成一个输入，重新规划一轮
```

即 agent-os 里 `clarification-superseded` 那套思路：后到的消息作废正在生成的回复，用最新状态重算。

## 3. 音频处理管线

### 3.1 进（用户 → 文本）

```bash
# 1. 下载原始资源（Ogg Opus 容器，不转码）
GET /open-apis/im/v1/messages/{message_id}/resources/{file_key}?type=file
# ⚠️ 语音必须传 type=file，传 image 拿不到

# 2. 转 16k 单声道 wav，给 ASR
ffmpeg -i in.opus -ar 16000 -ac 1 -c:a pcm_s16le out.wav

# 3. 同时转一份 16k mp3 留着给发音评测（Azure 接受 wav/ogg，wav 更稳）
# 原始 opus 也保留，复盘时可以让用户回听
```

**保留原始 opus**。复盘时可以「你当时是这么说的」放一遍原声，比对 bot 的标准音 —— 这是最有效的反馈形式，成本为零。

### 3.2 出（文本 → 语音）

```bash
# 1. TTS 出 mp3（MiniMax / Azure TTS 均可）
# 2. 转 opus —— 飞书只认 opus 容器
ffmpeg -i reply.mp3 -c:a libopus -b:a 24k -ar 16000 -ac 1 reply.opus
# 3. 读真实时长，别用估算
ffprobe -v error -show_entries format=duration -of csv=p=0 reply.opus
# → 例如 4.32 秒，× 1000 取整 = 4320
```

```jsonc
// 4. 上传
POST /open-apis/im/v1/files
{ "file_type": "opus", "file_name": "reply.opus", "duration": "4320" }
// → { "file_key": "file_v3_xxx" }

// 5. 发送
POST /open-apis/im/v1/messages?receive_id_type=chat_id
{
  "receive_id": "<chat_id>",
  "msg_type": "audio",
  "content": "{\"file_key\":\"file_v3_xxx\",\"duration\":4320}"
}
```

`duration` 填错会导致进度条错位或直接发送失败。

### 3.3 语音参数选择

| 参数 | 建议 | 理由 |
|---|---|---|
| 采样率 | 16 kHz | 语音够用，文件小，TTS 源多半也是 24k/16k |
| 码率 | 24–32 kbps | 20s ≈ 60–80KB，远低于 30MB 上限 |
| 声道 | 单声道 | |
| TTS 语速 | A2 场景 0.9×，B2 场景 1.05× | 语速本身是教学杠杆 |

## 4. bot 输出

### 4.1 输出形态矩阵

| 场景 | 形态 | 理由 |
|---|---|---|
| 对话中 | **只有语音** | 给了文字人就不听了 |
| 对话中（兜底） | 文字 | ASR 没听清 / TTS 失败 / 长指令 |
| 会话末 | 语音（1 句）+ 卡片 | 语音给情绪，卡片给抓手 |
| 复盘 | 文档 + 卡片链接 | 需要反复看 |
| 跟读 | 语音（示范）+ 卡片 | |

**对话阶段绝不同时发文字。** 唯一例外是故障兜底。

### 4.2 回复内容约束（写进 system prompt）

- 1–3 句，30 词以内
- 每轮必须有**一个推进动作**：追问 / 反问 / 给新信息
- 不要总结用户说过的话（浪费时间，也不像真人）
- 重铸时自然带出正确形式，不点破
- 不用「Great! Excellent!」这类空洞肯定 —— 每轮都夸会让反馈贬值

### 4.3 LLM 输出契约

必须是 JSON，因为状态机要吃结构化字段：

```jsonc
{
  "say": "Oh, what kind of movies do you usually go for?",   // 只念这一句
  "beat_progress": { "beat_id": "smalltalk-1", "done": false, "advance": true },
  "flags": [
    {
      "turn": 3,
      "type": "collocation",           // grammar | collocation | vocab | fluency | comprehension
      "said": "I very like this movie",
      "better": "I really like this movie",
      "why": "very 不能直接修饰动词，用 really 或 like it a lot",
      "severity": 2                     // 1=不影响理解 2=略影响 3=影响理解
    }
  ],
  "stuck": {                            // 卡壳点，没有就 null
    "at_turn": 3,
    "signal": "long_pause",             // long_pause | topic_switch | chinese | self_repair
    "intended": "想表达『这个电影的配乐很棒』但说不出来",
    "missing_phrase": "The soundtrack is fantastic."
  },
  "session_signal": "continue"          // continue | wrap_up | end
}
```

`session_signal` 是结束判定的一环。`stuck` 和 `flags` 直接喂给复盘，不需要第二次 LLM 调用——**复盘是攒数据不是重新推导**。

## 5. 结束判定

四个来源，任一触发：

| 触发 | 判定 | 优先级 |
|---|---|---|
| 用户显式 | 发文字 `/end`、`/stop`、`/结束`；或语音里说 "let's stop / I'm done / 结束吧"（ASR 文本关键词，只在中英关键词都命中且句长 < 8 词时才判） | 最高 |
| 目标达成 | 所有 `beats` 的 `done_when` 都满足 → LLM 给 `session_signal: "wrap_up"` → bot 说一句收尾 → 结束 | 高 |
| 静默超时 | 10 分钟没有新语音（定时器） | 中 |
| 硬上限 | 30 轮 或 15 分钟 | 兜底 |

> 关键词判定要保守。用户说 "I don't want to stop" 不该结束。所以关键词只在**短句**里生效，长句交给 LLM 判断。

### 收尾话术

结束不是静默消失，要有明确句点：

> "Alright, that's all I needed. Thanks — give me about half a minute and I'll send you the breakdown."

然后立刻进 `POSTMORTEM_BUILDING`，30 秒到 2 分钟内交付。

---

## 6. 复盘交付

结束后的产物，**分三批发**，不要一次性糊一大坨：

### 第一批（结束 + 15s）

一条语音 + 一张卡片：

```
🎯 今天专注：把「为什么」说清楚
━━━━━━━━━━━━━━━━━
最影响理解的一点
  I very like → I really like
  （very 不能直接修饰动词）

今天卡住 2 次 · 长停顿 5 次 · 语速 112 wpm
━━━━━━━━━━━━━━━━━
[ 看完整复盘 ]  [ 练 3 个发音 ]
```

### 第二批（+30s）

飞书文档，逐句三层对照。见 [04-数据与落盘](04-数据与落盘.md) 的模板。

### 第三批（用户点「练发音」后）

跟读关卡，见 §7。

> **为什么分批**：一次性发完，用户只会看第一屏。先给「最该改的一点」，等他有兴趣再展开。

## 7. 跟读关卡（第二周）

### 7.1 词从哪来

复盘时自动挑 3 个：

1. `flags` 里 `severity >= 2` 且 `type` 与发音相关的词
2. ASR 词级置信度最低的 2–3 个实词（去掉 the/a/of 这类虚词）
3. 用户之前错过的、还在复习队列里的词（优先）

**不要超过 3 个。** 3 个能做完，8 个做不完。

### 7.2 交互（关键设计：一次搞定）

```
bot:  卡片「今天的 3 个音」
       1. movie    /ˈmuːvi/     ← /v/ 咬唇
       2. soundtrack /ˈsaʊndtræk/
       3. fantastic /fænˈtæstɪk/
      + 一条语音示范（依次读这 3 个词）

用户: 一条语音，依次读这 3 个词

bot:  Azure 发音评估，参考文本 = "movie soundtrack fantastic"
      按顺序映射到 3 个词 → 音素级诊断 → 卡片回帖
```

**为什么合成一句**：分 3 次发 3 条语音，用户会烦；靠「回复某条消息」定位词，操作门槛高。合成一句 + 顺序映射，一次交互拿全。

风险：用户读的顺序错 / 漏读。用 Azure 返回的 word 序列对齐兜底 —— 对不上的词标记「没听到，再读一次」。

### 7.3 评估输出

```jsonc
{
  "words": [
    {
      "word": "movie",
      "score": 62,
      "phonemes": [
        { "ipa": "m", "score": 95 },
        { "ipa": "uː", "score": 88 },
        { "ipa": "v", "score": 31, "issue": "发成了 /w/，缺少上齿咬下唇" },
        { "ipa": "i", "score": 90 }
      ]
    }
  ]
}
```

**只给具体音，不给总分。** 「movie 的 /v/ 只拿到 31 分，你发成了 /w/」比「发音 62 分」有用一百倍。

### 7.4 错词进队列

`score < 70` 的词进 `review-queue.json`，下次场景里有权重加成，并在 3 天后复现。

## 8. 故障处理

| 故障 | 处理 |
|---|---|
| ASR 空结果 / 置信度极低 | 文字回：「没听清，再说一次？」（不消耗轮次） |
| TTS 失败 | 降级发文字，并在卡片上标注「语音服务异常」 |
| 上传 / 发送失败 | 指数退避重试 3 次；仍失败则文字回退 |
| 进程重启 | `runtime.json` 里存「当前 turn 处理到哪一步」，重启后从断点续；已发出的消息不重发 |
| 飞书重推事件 | `event_id` 去重 |
| 用户中途发图片/文件 | 忽略，回一句「我们先用语音练」 |

### 不要做的事

- **不要在对话中提示「你刚才那句话有语法错误」** —— 会让人闭嘴
- **不要在等待时发「正在思考...」文字** —— 消息流会脏，用 reaction
- **不要结束时不打招呼** —— 用户会以为卡死了
