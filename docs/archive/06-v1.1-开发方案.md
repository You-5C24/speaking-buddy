## 二、交互模型：群 → 话题 → 一次练习

用户建群、建话题，bot 不建。这样 session 的边界由用户的动作定义，最不会歧义。

```
群：「口语练习」（话题群）
 ├── 话题「点单 · 10-25 12:25」
 │     ├─ 菜单（文字）
 │     ├─ 三句卡（文字）
 │     ├─ 热身轮（你 1 条语音 / bot 1 条语音）
 │     ├─ 开场语音 "Hi! What can I get for you today?"
 │     ├─ … N 轮 …
 │     └─ 复盘卡片
 └── 话题「自由聊 · 10-26 08:10」
       └─ …
```

### session 的键

沿用 agent-os 已经跑通的写法（`agent-os/src/core/session-manager.ts:45-51`），话题 id 取三段回落：

```ts
const topicId = m.threadId || m.rootId || m.chatId;
const sessionKey = `${m.chatId}:${topicId}`;   // 带上 chatId，防不同群的 id 撞车
```

- **话题群**：`thread_id` 有值 → 每个话题独立
- **普通群里「回复某条消息」**：没有 `thread_id`，但有 `root_id` → 回复链也算一个话题
- **普通群 / 单聊**：两者都没有 → 退回 `chat_id`，退化成「一个对话框一场长会话」
- 群名、话题名只给人看，**程序只看 id**。别去匹配标题

`thread_id` / `root_id` 现在都没进 `IncomingVoice`（`src/lark.ts:23`），v1.1 要加。

**第一条消息的 id 可能不全。** 话题根消息到达时如果还没有 `thread_id`，会话会被登记在 `root_id` 或 `messageId` 下；第二条消息带着 `thread_id` 回来，就找不到它了——第一个会话变孤儿，菜单和热身白做。

所以**发完第一条回复后，用 reply 响应里回来的 `thread_id` 把同一个 sessionId 重新登记一次**。不要指望事件字段一次就给全。

### 回复必须落回同一个话题

反过来同样重要：在话题群里发一条**不带锚点**的消息，飞书会把它当成**一个新话题**。bot 说一句「建个话题开始练」，就凭空多出一个空话题。

`receive_id_type` **没有 `thread_id` 这个值**（只有 `open_id / union_id / user_id / email / chat_id`），所以不存在「直接往某个话题里发」的接口。唯一的路是回复消息：

```ts
const anchorId = m.rootId || m.messageId;   // 话题内所有回复都挂在根消息上
await client.im.v1.message.reply({
  path: { message_id: anchorId },
  data: { msg_type, content, reply_in_thread: hasThread },   // 单聊传 false
});
```

好消息是语音也一样走 reply——`msg_type: 'audio'` 用在 reply 上没问题，只是要先 `file.create` 拿 `file_key`。

代价：`sendText` / `sendOpus`（`src/lark.ts:120`、`:136`）现在只接 `chatId`，两个都要改成接「锚点消息 + 是否落在话题里」。**这是本版动得最深的一处**——语音回复是本产品的主要输出，打错地方整个产品就不成立。

`hasThread = !!m.threadId || !!m.rootId` 这个布尔值在 agent-os 里是现成的（`agent-os/src/index.ts:244`），所有回复都带它，照抄即可。

顺带一个边角：**被拉进群那个事件没有可回复的消息**，只能用 `message.create(chat_id)`，在话题群里它会变成一个新话题。可接受（正好当「开始」话题），但要知道它会发生。

| 场景 | bot 动作 |
|---|---|
| 被拉进群（`im.chat.member.bot.added_v1`） | 发一句说明：「建一个话题就是一次练习。在话题里说一句开始。」 |

**菜单不发卡片，用纯文字。** 手机上回一个数字比点按钮快，且不需要开 `card.action.trigger` 回调。


菜单由 `config/scenarios/index.json` 生成，**不手写**——列了没实现的场景（比如退货）就是一个死链，用户回 `2` 什么也不会发生。加场景时只改数据，见 [§4](#四场景配置-v2)。

> 上一稿这里写的是「回数字。直接发语音 = 从 1 开始」。**这句删掉了**：认不出来就默认开局，等于替用户选了场景，而 §11 的验收脚本第一句正好是「发一句 hi」——按旧规则它会掉进自由聊，整条核心验收（店员听错、热身、块闭合）一条都不触发。认不出就发菜单，是「我还不知道练什么」这个状态唯一的出口。

### 2.1 话题根消息就是选题

**前提（已确认）：飞书话题群里，话题标题就是首条消息的内容**，两者是同一件事。

由此得到一条硬规则：**选题只读首条消息的正文，永远不读标题。** 事件里只有消息正文、没有标题，而且用户事后能改标题——读标题会在「用户改了标题」那一刻和正文漂移。标题只给人看。

#### 根消息的语义：不是模式开关，是种子

| 根消息内容 | bot 动作 | 备注 |
|---|---|---|
| 数字（`1`）或场景短名（`点单` / `自由聊` / `cafe` / `free`） | 直接进该场景，**跳过菜单** | 精确匹配，见下面的词表 |
| 认不出的文字（`hi` / `练口语` / 空） | **发菜单，不默认开局** | 菜单是「不知道练什么」的唯一出口 |
| 一段有内容的话（`今天去爬山了`） | 进自由聊，**把这段话当种子** | 去掉标点和空白后至少 4 个字。更短的发菜单。只在这场练习还不存在时 |
| 单聊里第一条就是语音 | 发菜单 | 单聊没有「首条必须是文字」这个前提 |

**「模式分流」不要写成 `if (自由) {…} else {…}`。** `free-1` 在 §4 里已经是一个场景，和 `cafe-1` 结构完全相同，只差「没有 goal、没有 beats」。一条流程走到底，差别全部由 JSON 表达——否则自由聊拿不到热身、块统计、`/end` 复盘，以后每加一个功能都要写两遍。

**为什么是「种子」而不是「模式」**：自由聊真正的问题是「随机开一个话题，用户没内容可说」，而根消息恰好给了一句现成的种子文案，零额外成本（文字本来就已经收到了）。

```
用户（根消息）：今天去爬山了
bot：Mountain hiking? Nice. How long did you walk?
用户：Three hours, and now my legs hurt.
bot：Three hours! Was it steep?
```

这和「Hey, what's been going on today? → Nothing much. → 话题死掉」是两回事，后者就是 acf8 那种失败。

#### 短名词表由 `index.json` 生成，不手写

短名匹配和菜单一样，**必须从数据生成**，否则加场景时又是一个「列了没实现」的死链：

```jsonc
[
  { "id": "cafe-1", "title": "点单 · 店员会听错一次", "level": "A2",
    "aliases": ["1", "点单", "点餐", "买咖啡", "cafe"] },
  { "id": "free-1", "title": "自由聊 · 随便说，我接住", "level": "A2",
    "aliases": ["2", "自由聊", "随便聊", "free"] }
]
```

匹配规则：**归一化后整句相等**（沿用 §3 的 `norm()`），不做模糊包含。原因：

- 包含匹配会让 `我不想点单` 命中 `点单`，用户想要什么都会反着来
- 模糊匹配（拼音、编辑距离）在 `hi` 这种输入上误判率太高，而且无法解释

认不出就发菜单，**代价只有一条消息，比错误开局便宜得多**。别名对不上是常见情况，不是异常——别为了「聪明」把它做成猜测。

> **认不出之后有第二条路**：如果这句话是个请求（`我想做机场话题`），走 §4.5 的生成，而不是直接掉进菜单。归属哪个场景由 §4.5 的分类决定，**仍然不靠模糊匹配**。

#### 根消息的残留问题

- **root 落盘后崩溃**：如果进程崩在「收到根消息」和「写好 `meta.json`」之间，扫盘扫不到 session，而根消息内容已经不在事件里，**无法重新推导用户选了什么**。两个补丁都要做：`meta.json` 存一份 `rootText`；以及「话题里来了一条语音但找不到 session」时回菜单，不要沉默。
- **数字命中但场景已结束时**：按 §8 的规则回「这次练习结束了，开个新话题继续」，不重开。
- **单聊退化**：单聊里没有话题，`sessionKey` 退化成 `chatId`，一段对话一场练习；菜单和短名照常可用，只是「建话题=选题」这一步不存在。

### 权限与阻塞

> 🔴 **动手第一天先验这一条。这一条不通，整个群模型作废，只能退回单聊。**

飞书 bot 在群里默认**只收到 @ 自己的消息**（`im:message.group_at_msg:readonly`）。而**语音消息没法 @ 人**——所以群里发语音，bot 一条都收不到。

必须申请 **`im:message.group_msg`（获取群组中所有消息）**，并且把 `src/lark.ts:210` 那行 `chat_type !== 'p2p'` 的过滤改掉。

⚠️ **`group_msg` 是敏感权限，要走发布审核，不是后台点一下就生效。** 没通过时平台的表现就是「群里不 @ 就没反应」。所以这一条不能当成「验证一下」，要当成「提一个申请」——**今天就去提交**，审核期间先做不依赖它的部分。

验证动作：
1. 建话题群，拉 bot 进去
2. 在话题里发一条纯语音（不 @）
3. 确认事件到达，且 `thread_id` 和 `root_id` 至少有一个非空、`chat_type === 'group'`、`chat_mode === 'topic'`
4. 回一条带 `reply_in_thread: true` 的消息，确认它落在原话题里而不是新开一个

**退化路径只有一个：拿不到 `group_msg` → 留在单聊，本版交互模型作废。** 上一版写的「一个群一场练习」是假的——语音不能 @，没有 `group_msg` 一样收不到，括号里那句自己也承认了「仍然不通」。别留着这句话给人错觉。

单聊下其余设计全部保留：三句卡、热身、beats、块统计、`rewrite` 都不依赖话题，只是 `sessionKey` 退化成 `chatId`，一段对话一场练习。

## 三、练前预习：三句卡 + 强制热身

这是这一版最核心的功能。对应教学法上的 **TBLT pre-task**（Willis 三段式的第一段）和 Ellis 的 pre-task planning 研究：开口前给 2–3 分钟准备，输出的复杂度、准确度、流利度都会上升。

你现在的处境是「零准备 + 必须临场组句」，研究里这是最差的组合。

### 卡的形态

```
━━━ 点单 · 店员会听错一次 ━━━
今天用这三句，别的不会说也没关系：

1  Could I get a ___ ?
   Could I get a medium latte?
   也可以换：medium Americano / large iced coffee / oat milk latte

2  For here, please.
   或者：To go, please.

3  Sorry, I meant ___ .
   Sorry, I meant oat milk, not soy.

准备好了发一条语音，先用 1 号句造一句。
```

### 颗粒度：整句 + 一个槽

三种颗粒度里选中间那个：

| 形态 | 例子 | 问题 |
|---|---|---|
| 词 | `coffee` | 你已经会了，没有价值 |
| **块 + 槽** | `Could I get a ___ ?` | **选它**：有整句兜底，又有槽位逼你换词 |
| 整句 | `Could I get a medium latte, please?` | 只能照念，检索量最小 |

「组句」的最小可行版本不是从零件搭句子，是**换一个零件**。对 A2 这已经够难，而且不会把你打回沉默。

### 强制热身（不可跳过）

热身不是可选步骤，是**这一步必然发生**：

```
① 你发一条语音，用 1 号句造一句
② bot 回：Nice, a medium latte. Okay — Hi! What can I get for you today?
   （前半句是重铸，后半句是开场。合成一个轮次，不额外多一轮）
```

这一步的价值：**把最难开口的第一句挪到无风险状态**。人第一次开口的心理门槛，比后面九轮加起来都高。

约束：
- 热身轮单独落 `turns/000-warmup/`，**不计入正式轮次**
- **但块统计要连热身一起扫。** 用户唯一一次用 1 号句的地方就是热身，只扫正式轮次的话卡片上 1 号块永远是 ✗
- 你在热身里说了别的话（没用 1 号句），**也照常进入场景**，不重来、不提示、不卡住。只在复盘记一笔
- 「不可跳过」指的是这个步骤存在、bot 等你这一个语音轮次；不是指拒绝前进
- `atTurn` 一律指**正式轮次**，热身不占号。热身的重铸不会把 beat 推后

### 热身那句「重铸 + 开场」是模板，不调 LLM

`Nice, a medium latte. Okay — Hi! What can I get for you today?` 的前半句如果靠 LLM 生成，等于在首轮多加一次 2 秒延迟和一个失败面，而此时用户正等着听第一句话。

做法：**抽当轮转写里的实词填模板**。

```ts
// 从 ASR 结果里取置信度最高的 1-2 个名词短语，塞进模板
`Nice, a ${noun}. Okay — ${scenario.opening}`
```

抽不出来（用户说了句完全无关的话）就退回纯开场 `Okay — ${scenario.opening}`。坏处是重铸可能生硬，好处是**这一步不可能出错、不可能慢**。热身的目标是「让第一句话没有门槛」，不是「给一次完美的重铸」。

### 复盘验收：防短语本

卡片上多一行：

```
三句用了两句：1 ✓  2 ✗  3 ✓
```

这是整件事的**闭合机制**。没有它，三句卡只是一张传单；有了它，块和任务之间形成回路。

实现很便宜：拿当轮 ASR 文本做**归一化之后**的子串匹配。**不要自己再写一份 `norm`**，统一用 `src/blocks.ts` 里那个（已落盘并自检）。

```ts
import { matchesBlock, computeBlockUsage } from './blocks.js';

matchesBlock(block, asrText);                    // 单块
computeBlockUsage(blocks, textsIncludingWarmup); // 全部块，含热身轮
```

`norm()` 的定义在 `src/blocks.ts`，和本文档早期草稿的写法有**两处实质性不同**，都是踩过的坑：

- **保留任意语言的字母**（`\p{L}`）。草稿写的是 `[^a-z0-9' ]`，那会把 `norm('点单')` 变成空串——§2.1 的中文别名会静默失效
- **NFKC + 弯引号归一**。`I’d like` 和 `I'd like` 必须是同一个东西（iOS 输入法会给弯引号）

**归一化是必须的，不是讲究。** `asr.py:64` 的 text 是 `" ".join(w.word.strip())`——whisper 的 word 不带标点。所以：

- 模式里写 `"sorry, i wanted"` 永远命中不了（转写里没有逗号）
- 写 `"i'd like"` 大概率命中不了（whisper 常输出 `I would like`）

规则：**`match` 里只放纯小写、无标点的形式**，缩写要在数组里同时写两种拼法。`"could i get"` 这种是安全的，`"sorry, i wanted"` 要改成 `"i wanted"`。

```ts
match: ['could i get', 'can i get', "i'd like", 'i would like', "i'll have", 'i will have']
```

**允许误判。** 这是个提醒，不是考试；不做分数（04 §1 红线）。

### 选块标准：三条，缺一不收

1. **这个任务里我一定得说它** —— 否则是短语本
2. **换个话题我就不说了** —— 否则是通用句型库（04 §1 红线）
3. **说了对方一定听懂** —— 不靠语调、不靠连读

按这三条筛，**`I'm kinda ...` 进不了 A2 第一批**。它是语用上的模糊限制词（hedging），作用是让语气松一点，属于「听着像母语者」的装饰，不是「把想说的说出来」的工具。而且 `kinda` 的发音没到位，说出来更像含糊。

`I'm gonna ...` 频率极高，但**点单任务里用不上**——它属于自由聊的卡，不属于点单的卡。这正好印证「每场景一小组」，不是全局句型库。

### 类型要跟着改

`Scenario`（`src/pipeline.ts:13`）现在是 `goal: string` 必填、`beats: {need, hint}[]`。v2 之后：

```ts
export type Block = {
  n: number;
  frame: string;                  // "Could I get a ___ ?"
  example?: string;
  swaps?: string[];
  alternatives?: string[];        // 同义说法，同样带 ___（§4.5）

export type Beat = {
  atTurn: number;                 // 正式轮次，热身不占号；生成时钳到 [2, 3]
  need: string;
  directive: string;
  forBlock?: number;              // 这个 beat 给哪一块开口。还没轮到则卡片记 not_reached，不是 unused
};

export type Scenario = {
  id: string;
  title: string;
  level: string;
  goal?: string;                  // free-1 没有
  hiddenGoal?: string;            // free-1 有；只进 prompt，不进卡片
  aliases?: string[];             // §2.1 的短名；由 index.json 汇总
  persona: string;
  opening: string;
  voice?: string;

```

`config/scenarios/cafe-1.json` 已是运行时读的那份。`config/scenario.json` 已删，`pipeline.ts` 通过 `loadScenario(id)` + `resolveScenario()` 取场景。

`src/scenarios.ts` 里那份 zod schema 就是上面这个类型的运行时版本——**改类型时必须同时改 schema**，否则空字段会被 zod 拒掉或悄悄放过，两种都比编译错误难查。

### 菜单由 `index.json` 生成，不要手写

上一稿把菜单写死了三项，其中「2 退货」却排在 P1——**P0 跑验收时用户回 `2` 会得到一个死链**。

菜单必须从 `index.json` 渲染：


加场景时只改数据，不改 `index.ts`。没有的项不会出现在菜单里，死链问题自然消失。

### beat 由代码注入，不靠模型自觉

```ts
const beat = scenario.beats.find(b => b.atTurn === turnIndex);
// beat 存在时，在 system prompt 末尾追加一段
if (beat) system += `\n\nTHIS TURN ONLY: ${beat.directive}`;
```

**为什么不用状态机、也不让模型自己推进**：「店员听错一次」如果只是 prompt 里的一句软要求，它会在某轮悄悄消失——acf8 就是一次都没发生。按轮号注入是确定性的，代价只有几行。

`atTurn` 用固定轮号而不是「满足条件才触发」，是因为用户不一定按剧本走（第 2 轮可能只说了 `No.`）。第 2 轮说什么都会被听错，这本来就是真实店员的行为。

**轮号要压在会话可能结束之前。** acf8 那 6 轮里 4 轮 ≤ 4 词，很可能第 3 轮就 `/end`。原来的 `atTurn: 4` 意味着 2 号块（`For here / To go`）永远没机会触发，而卡片上会记成 `2 ✗`——**这是把「会话太短」记成了「你没用」，归因错了**。所以提前到第 3 轮。

配套：`blockUsage` 要能区分「没触发」和「触发了但没用」：

```jsonc
"blockUsage": { "1": "used", "2": "unused", "3": "not_reached" }
```

卡片上 `not_reached` 显示 `—` 而不是 `✗`。理由和 §7 的 `null vs 0` 一样：两种不同的意思不能用同一个符号。

### 自由聊：`free-1`

```jsonc
{
  "id": "free-1",
  "title": "自由聊",
  "level": "A2",
  "persona": "a patient friend who is genuinely curious. You speak plainly and never lecture.",
  "opening": "Hey. What's been going on today?",
  "blocks": [
    { "n": 1, "frame": "How do you say ___ in English?", "match": ["how do you say"] },
    { "n": 2, "frame": "What's another word for ___ ?", "match": ["another word for"] },
    { "n": 3, "frame": "Sorry, can you say that again?", "match": ["say that again", "repeat that"] }
  ],
  "beats": [],
  "hiddenGoal": "讲完一件完整的小事（谁、什么时候、发生了什么），并在中途至少反问一次"
}
```

自由聊的三句卡不教话题词汇，教**求助用的元语言**。理由是：自由聊里你卡住的时刻全是「这个词我不会说」，而这句卡就是那时的出口。

> ⚠️ 这三句只能解决一半。真到「拿铁怎么说」的时候你还会蹦中文，而 `small.en` 会把中文硬转成乱码英文。见 [§9 P2](#p2-可以这一版不做)。

自由聊**不设 goal、不设 beats**，但仍然记 `flags`、仍然出复盘。不逼目标，不等于不记录。

#### `hiddenGoal`：没有目标会塌

`04 §2` 的结论是：没有目标，对话 20 分钟内必然塌缩回你最熟的 20 个句式。「自由聊」如果真没有任何隐性方向，它就是你论证过会失败的那个东西。

所以 free-1 有 `hiddenGoal` 但**没有 `goal`**，两者不是一回事：

| 字段 | 是什么 | 进 prompt | 进卡片 |
|---|---|---|---|
| `goal` | 场景任务，用户可见的目标 | 是（`Scenario goal:` 那行） | 是（卡片标题下的场景说明） |
| `hiddenGoal` | bot 的隐藏议程 | 是（「自然地推动，不要说破」） | **否** |

当前值「讲完一件完整的小事 + 中途反问一次」是按 04 §2 的标准挑的：有完成的判据，且用户不需要知道它。**不是 `beats`**——`beats` 按轮号强制注入，自由聊的对话走向不可预测，硬塞会变成「第 2 轮必须干嘛」，那就不自由了。

#### 自由聊也有热身，任务是用一句话说种子

**不跳过热身。** 自由聊的第一句门槛比点单高，不是低：

| 场景 | 用户手里有什么 | 第一句的门槛 |
|---|---|---|
| 点单 | 菜单 + 情境 + 三句卡 | 低 |
| 自由聊 | 只有一个话题名，什么都没有 | **更高** |

"Hey, what's been going on today?" → "Nothing much." → 话题死掉。这跟 acf8 里「4 轮中有 4 轮 ≤ 4 词」是同一个失败，只是没有兜底。

free-1 的热身任务是：**用 1 号块之外的方式，一句话说出这次聊什么**。具体做法：

```
① 根消息里已经有种子（「今天去爬山了」）→ 三句卡末尾换成：
   准备好了发一条语音，先用英文说一句你今天干嘛了。
② 根消息里没有种子（用户直接点了「2」）→ 三句卡照常，热身任务改成：
   准备好了发一条语音，随便说一句你今天做了什么。

③ bot 回：Hiking — nice. Okay — what was the best part?
   （前半句接种子，后半句是开场，合成一个轮次。走 §3 的模板重铸，不调 LLM）
```

热身同样落 `turns/000-warmup/`、同样计入块统计、同样不占 `atTurn`。**free-1 和 cafe-1 在流程上没有一处不同。**

#### 自由聊的卡片：`rewrite` 计数，不显示块使用

free-1 的三句是求助用语，只在卡壳时出现。一次聊得很顺的对话，块使用行会是 `1 ✗ 2 ✗ 3 ✗`——**这等于惩罚一次成功的聊天**，和 §3 里 `atTurn: 4` 那个「把会话太短记成你没用」是同一类归因错误。

按 `cardStyle` 分叉，只换卡片，不换流程：

```jsonc
// cafe-1
"cardStyle": "blocks"
// free-1
"cardStyle": "rewrite"
```

| 卡片行 | `blocks` | `rewrite` |
|---|---|---|
| 标题下 | `三句用了两句：1 ✓ 2 ✗ 3 ✓` | `说得更地道 3 处 · 6 轮 · 语速 115 wpm` |
| 块使用 | 显示 | **不显示** |
| `topIssue` | 有 | 有（同样的规则：只在 `severity >= 2` 时出现） |
| 每轮「更自然」 | 有 | 有 |
| 指标底栏 | 有 | 有 |

`rewrite` 计数 = 卡片上「更自然」行的条数（即通过 §5 两条校验后留下的 `rewrite` 数量），不需要另算。

> 这条只改渲染，`postmortem` 里的 `blockUsage` 照常落盘——free-1 的块仍然要统计，只是不上卡片。想看的时候在 JSON 里能看到。

### 4.5 场景来源：固定 JSON vs 生成

> **这一版不实现生成，只把边界划好。** 下面全是设计，不是本版 P0 的活。
> 写进来的理由：`Scenario` 的类型、`blocks[].match` 的派生方式、`meta.json` 要不要存快照——这三件事如果按「只有手写 JSON」的前提定死，以后加生成要返工。

#### 结论：生成可行，但方向要拧一下

**不要每轮现场生成，要首次生成 + 落盘 + 之后查表。**

| 做法 | 生成时机 | 代价 |
|---|---|---|
| ❌ 每轮现场生成 | 每次用到场景都调一次 LLM | 不可复现、块编号漂移、复盘和未来的 SRS 全部失效 |
| ✅ **首次生成 → 落盘 → 查表** | 只在一个新请求第一次出现时调一次 | 零额外成本，且保留全部灵活性 |

第二种做法里，**LLM 是场景的作者，不是场景的运行时。** 它产出的 JSON 和 `cafe-1.json` 是同一类东西：能打开看、能手改、能提交进 git。

场景结构本身很小（`title / goal / persona / opening / blocks(3) / beats(2)`），这个体积的生成是稳的；而热身走 §3 的模板重铸、不调 LLM，所以第一句语音的 5 秒预算不受这条影响。

#### 三级路由

```
第 0 层  精确别名命中（"1" / "点单" / "机场"）          → 直接读 JSON，不调 LLM
第 1 层  请求句（"我想做机场话题" / "来个酒店 check in"） → LLM 生成 → 落盘 → 进流程
第 2 层  认不出（"hi" / 空）                            → 发菜单
```

**第 0 层永远在，不因为有了 LLM 就删掉。** 内置场景固定成 JSON，不依赖任何模型调用——它是兜底，也是 §11 验收脚本要跑的那条路。

生成成功后，把请求句里的关键词补进该场景的 `aliases`（如 `["机场", "坐飞机", "值机", "airport"]`），**下次同一个说法直接走第 0 层**。用得越多，LLM 调用越少。

第 1 层的产物落到 `config/scenarios/generated/<slug>.json`，和手写场景同构；`index.json` 里加一个 `generated: true` 字段区分来源（只影响 display，不影响流程）。

#### 🔴 生成物有四条确定性校验，缺一条就不能用

生成 prompt 管不住模型，下面每一条都必须用代码验，验不过 → 降级到菜单，**不把半成品发给用户**。

| # | 校验 | 不过的原因 |
|---|---|---|
| 1 | `blocks.length === 3` | 少于 3 块闭合不成立；多于 3 块 §3 的「三句卡」就散了 |
| 2 | 每块拆槽后 **≤ 8 词** | 超过就是 B1/B2 的句子，A2 念不出来 |
| 3 | 禁用词表：`kinda / sorta / gonna / wanna / I was wondering` | §3 已经逐条论证过这些进不了 A2 第一批 |
| 4 | `beats` 里至少一条**带明确摩擦动作**（听错 / 误解 / 反问 / 打断） | 没有摩擦的场景是纯角色扮演，用户三句之后不知道干嘛 |

再加一条钳制：**生成时强制 `atTurn ∈ [2, 3]`**。§4 的教训是「6 轮里 4 轮 ≤ 4 词，很可能第 3 轮就 `/end`」，`atTurn: 4` 等于永远不触发。

#### 🔴 `match` 由代码从 `frame` 派生，不让 LLM 写

`blocks[].match` 是块闭合的唯一依据。§3 已经踩过一次：`"sorry, i wanted"` 带标点永远命中不了（whisper 输出没有标点）；`"i'd like"` 大概率被转成 `"I would like"`。

**LLM 会写出看起来完全正确、实际永远命不中的 match 模式，而且失败是静默的**——卡片上显示 `1 ✗`，你会以为用户没说，其实是匹配没中。

所以：**LLM 只给 `frame` 和同义说法，`match` 由代码拆槽位生成。**

```ts
// LLM 返回：{ frame: "Sorry, I meant ___ .", alternatives: ["Sorry, I wanted ___ ."] }
const parts = [frame, ...alternatives]
  .flatMap(f => f.split('___'))
  .map(norm)
  .filter(Boolean);   // → ['sorry i meant', 'sorry i wanted']
```

这样模型只写它擅长的（英文句子），不写它不擅长的（匹配模式）。手写 JSON 也走同一条派生逻辑，**两种来源共用一条代码路径**——这是本节的类型设计要提前落地的原因。

#### 🟡 「请求」和「种子」会打架

这是这个方案里唯一的结构性歧义：

```
"我想做机场话题"   → 这是请求，要生成场景
"我想去看电影"     → 这是种子，要进自由聊
```

两句话形状一样，纯规则分不开。做法是**让同一次 LLM 调用顺便做分类**，返回：

```ts
{ mode: 'scenario' | 'free' | 'menu', scenario?: {...}, seed?: string }
```

反正已经调了一次，多判一个字段不增加延迟。而且**误判代价很低**：三句卡第一行会写「给你准备了一个机场值机的场景」，用户一眼看出理解错了，回一句「不对」或 `/switch` 就行。

但**不要指望这个分类永远对**。它的作用是「大多数情况省一条消息」，不是「取代菜单」——第 2 层必须保留。

#### 🟡 生成物不可审、不可复现，要三个措施

固定 JSON 你能 review；生成的你不能——而这是**教学质量**问题，不是工程问题。

1. **落盘到 `config/scenarios/generated/<slug>.json`**，第一次生成后就是普通文件：可手改、可 git 提交、可删掉重来
2. **`meta.json` 嵌一份场景快照**（不是只存 `scenarioId`）。§8 说「meta 是恢复的唯一权威」，如果 generated 目录里那个文件被删了，历史 session 就复盘不了。快照 ~1.5KB，可接受
3. **块编号只在同一次生成内稳定**。重生成会换块，所以 P2 的跨会话 SRS 不能靠 `scenarioId:blockN`，**得靠 `frame` 本身**当键

#### 🟡 生成 prompt 里塞了用户原文

`"我想做机场话题"` 会进生成 prompt。自己用风险低，但仍要做两件事：长度截断（≤ 100 字）、用分隔符包起来。主要防的不是攻击，是用户手滑粘一大段东西把 prompt 冲掉。

#### 和现有设计的关系

| 现有设计 | 要不要改 |
|---|---|
| §2.1 整句精确匹配 | **保留**，作为第 0 层快路 |
| `aliases` 由 `index.json` 生成 | **保留**，生成的场景也产出 aliases |
| 认不出 → 菜单 | **保留**，变成第 2 层兜底 |
| `cardStyle` | 不动。它管渲染，和场景怎么来无关 |
| `hiddenGoal` | 生成的场景也带一个，同一次调用返回 |
| `Scenario` 类型 | 不用改，生成物就是它的一个实例 |

**唯一新增的是 `config/scenarios/generated/` 目录和一次额外的结构化调用。** §9 的 P0 一条都不用改。

#### ✅ 试跑结果（2026-10-25，已跑）

`src/probe-scenario-gen.ts`，`pnpm probe:gen -- 3 "话题A|话题B|话题C"`。**这是诊断脚本，自己发 HTTP，不经过 `llm.ts`，不改任何运行路径。**

跑了两轮：机场值机 5 次 + 酒店入住 3 次，然后机场 / 酒店 / 点餐各 3 次（9 次，跨三个话题）。共 17 次生成。

| 检查项 | 结果 |
|---|---|
| JSON 解析 | 17/17 |
| `validateScenario()` 八条全过 | 17/17 |
| 有摩擦 beat | 17/17 |
| 双槽位 frame | 0/17 |
| 切题 | 17/17 |
| 生成耗时 | 4.9s – 14.0s（平均 ~7s） |

**结论一：格式层面比预期稳。** 四条确定性校验一次都没触发过。这说明三件事：结构化输入下模型对「恰好 3 块、每块一个槽、≤8 词、必带摩擦」的理解是可靠的；§4.5 里那四条校验**仍然要写**（它们是防回退的，不是补漏洞的）；但**生成的主要风险不在格式**。

**结论二：真正的风险是内容，而校验抓不到。**

跨三个话题跑出来这几对：

```
cafe-1#1          ≈ order-at-cafe#2        1.00
hotel-check-in#1  ≈ hotel-check-in-name-confusion#1   1.00
order-at-cafe#1   ≈ fast-food-order#1      0.67
```

（骨架是 `could i have a _ seat please` / `could i have a _ room please` 这类，只换一个名词。）

这正是 §3 选块标准第 2 条要挡的东西——**「换一个话题我就不说了」不成立，那它就是句型库不是场景卡。** 一个 `Could I have a ___ , please?` 加一个名词，能覆盖点单、酒店、值机、买票全部场景。生成器很擅长产出这个，因为它在统计上最安全。

**所以：`validateScenario()` 是必要条件，不是充分条件。** 加了一个提醒式的检查：

| 新函数 | 位置 | 作用 |
|---|---|---|
| `frameSkeleton(frame)` | `src/blocks.ts` | 槽位归一成 `_`，只看句式 |
| `findGenericFrames(scenarios)` | `src/blocks.ts` | 跨场景比对骨架，多重集重合 ≥ 0.6 就提示 |

> ⚠️ 写这一版时踩了个坑，值得记：**`frameSkeleton` 不能先 `norm()` 再替换槽位**——`norm` 会把 `___` 连字母一起抹掉，骨架退化成普通句子，跨话题比对永远看不出「同一公式换名词」。必须**先按 `___` 拆、再逐段归一**。这个 bug 让第一版 `findGenericFrames` 恒返回空，看起来像「检查通过」。

**0.6 这个阈值没标定过**，只用于提示人工复核，**不要拿它自动删块**。真实用法是：生成后打印这几对，人眼看一眼——「这四条真是同一个句式吗」，是就改 prompt 或换块，不是就放过。

#### 这对 §4.5 后面三步的影响

| 步 | 原计划 | 现在要改的 |
|---|---|---|
| 3 生成 + 四条校验 + 落盘 | 校验过了就收 | **再加一道人工复核**：落盘前打印 `findGenericFrames` 的结果。或者更进一步——生成时要求「三个块分属任务的三个阶段」（下单 / 澄清 / 收尾），而不是三个同构句 |
| 4 分类合并 | — | 不变 |

**没有因为格式稳就放宽校验。** 反过来说：如果将来发现生成物长期过不了内容这一关，退路是「固定 JSON + 生成只负责换名词和措辞」，而不是「放宽标准」。

## 五、Prompt 变更

`src/llm.ts` 的 `RULES` 追加三条，其余不动：

```
- The learner is A2. Prefer questions they can answer in one full sentence:
  yes/no questions with a reason, A-or-B choices, "what kind of ___".
  Never ask an open question that can be answered with one word.
- Never ask "Anything else?" as your only question. It invites a one-word answer.
- Words in the transcript may be marked like [word? p=0.38] — that's an ASR
  guess. Never build a flag whose "said" is one of them, and never "correct" a
  neighbouring word just because it looks wrong next to a guess.
```

并在 `buildMessages` 里带上：

```ts
// goal 自 v2 起可选（free-1 没有），拼接前必须判空
if (goal) system += `\n\nScenario goal: ${goal}`;
if (blocks.length) {
  system += `\n\nBlocks the learner prepared (they may use these):\n` +
    blocks.map(b => `${b.n}. ${b.frame}`).join('\n');
}
// hiddenGoal 只进 prompt，不进卡片，措辞必须说明「不要说破」
if (hiddenGoal) {
  system += `\n\nYour own agenda this session (never state it, just steer): ${hiddenGoal}`;
}
// 自由聊的种子：只在这一处使用，不进卡片、不进复盘
if (seedText) system += `\n\nWhat they mentioned when starting: ${seedText}`;
```

`seedText` 放在 prompt 里而不是拼进 `opening`，是因为开场语音走 §3 的模板（`重铸 + opening`），不调 LLM；把种子拼进 `opening` 会让第一句变成一段生硬的复述。第一句话用模板接（`Hiking — nice. Okay — what was the best part?`），种子留给后面几轮展开。

> 种子**不进复盘卡片**。它只是开局素材，不是用户说的内容——把它当成「你说的」写进 `rewrite`，就又踩了 §1 缺陷 4 的变体。

### 置信度护栏

> ⚠️ 上一稿这里写错了，改过了。**原来的方案挡不住它自己举的两个例子**，别按旧版实现。

原来的做法是筛出 `p < 0.62` 的实词，另起一行 telling 模型「这些词别建 flag」。但对照 §1 的两条证据：

| 案例 | flag 卡在哪 | 旧方案的实际行为 |
|---|---|---|
| `as` p=0.52 被判「多余」 | `said = "as"` | 被 STOPWORDS 过滤，**进不了列表** |
| `pay` p=0.38 → `main` 被改成 `mean` | `said = "main"` | `main` 是高置信度词，**不在列表里** |

两个都漏。第二条更麻烦：`"pay"` 确实进了列表，模型收到的是「别碰 pay」，于是它继续把旁边的 `main` 改掉。**护栏要防的是「在可疑词邻域内动手」，不是「碰可疑词本身」。**

而且 0.62 这个阈值本身就站不住——表里 `Okay`=0.51、`Cash`=0.41 是真词，`as`=0.52、`pay`=0.38 是幻觉，**置信度不区分真假**。拿它当判据只能得到噪声。

#### 改成三层，从确定到启发

**第一层（必须有，零成本，确定性）：flag 的 `said` 必须是转写里的逐字子串。**

```ts
import { norm } from './blocks.js';   // §3 那个，不是草稿里的 [^a-z0-9' ]
const transcript = ` ${norm(words.map(w => w.w).join(' '))} `;

flags = flags.filter(f => {
  const said = norm(f.said);
  return said.length > 0 && transcript.includes(` ${said} `);
});
```

> 两处和草稿不同，都是必须的：**用共享的 `norm`**（保留中文，见 §3），以及**两侧补空格**——否则 `said = "get"` 会被 `target` 的子串命中，等于护栏自己放行了一条伪造的 flag。

模型编出来的片段（把 `main` 报成 `mean`、把没出现的词当原句）会被直接丢掉。这一条不依赖任何阈值，做完就能拦住「纠正一个没犯过的错」的大头。

**第二层（推荐）：不另起列表，把置信度内联到转写里。**

模型看到的是完整上下文，才能判断该不该动旁边的词：

```
What is the [main? p=0.46] pay [pay? p=0.38] at the register?
```

低置信度的词用方括号标 p，其余不动。prompt 里那句改成：

```
- Words marked like [word? p=0.38] are ASR guesses. Do not build a flag whose
  "said" is one of them, and do not "fix" a neighbouring word just because it
  looks wrong next to a guess — the guess is probably what's wrong.
```

比单独一个 `ASR was unsure about: "pay"` 有用得多——后者脱离上下文，模型无从判断该动哪里。

**第三层（可选）：不要 STOPWORDS 过滤。**

`as` 这类虚词恰恰是最常被幻觉出来的（acf8 那条就是）。过滤掉等于把最该标的藏起来。真要降噪，就只保留内联标注、不做额外筛选。

阈值仍然用 0.62 当**标注线**（标出来的只是提示，不是判据），但**不要再把它写成「已验证的分界线」**。acf8 的六条样本不足以标定，等 §7 说的 10 场数据再回来看。

原始分布（仅作参考，不足以支撑任何结论）：

| 词 | p | 真值 |
|---|---|---|
| `pay` | 0.38 | 幻觉（第 4 轮原文 `What is the main pay at the register?` 本身自相矛盾，标注待复核） |
| `Cash,` | 0.41 | 真词，但被拉长 |
| `Americano?` | 0.46 | 真词 |
| `as` | 0.52 | 幻觉 |
| `Okay,` | 0.51 | 真词 |
| `medium` | 0.94 | 真词 |

低置信度 ≠ 幻觉，所以**不是直接丢词，是不能在它上面或其邻域建 flag**。模型仍然看得见完整转录。

### 新增输出字段 `rewrite`

```ts
export const Reply = z.object({
  say: z.string().min(1).max(300),
  /** 用户这句话，母语者会怎么说。和原句一样就省略 */
  rewrite: z.string().max(200).optional(),
  flags: z.array(Flag).max(5),
});
```

prompt 里：

```
- "rewrite": if the learner's sentence could be said more naturally, write THEIR
  sentence the way a native speaker would. Same meaning, same length roughly.
  Not your own reply. Omit if nothing to improve.
```

这一条修缺陷 4。复盘卡片的「更自然」从此取 `rewrite`，**永远不用 `reply.say`**。

#### 但 prompt 管不住它，必须加两条代码校验

`jsonMode` 只是 `response_format: {type:'json_object'}`，**不强制 schema**（`src/llm.ts:166`）。可选字段不会被可靠地省略，实测模型很容易：

- 原句照抄一份回来 → 卡片上出现「你说：I want a medium Americano / 更自然：I want a medium Americano」，**这就是缺陷 4 的变体**
- 给一句本来没问题的句子配一个改写 → 暗示用户说错了，违反 04 §1 第 3 条红线

```ts
// 归一化后与原句相同 → 丢弃
if (reply.rewrite && norm(reply.rewrite) === norm(userText)) delete reply.rewrite;
// 这一轮没有 flag → 不输出 rewrite（没东西可改）
if (reply.flags.length === 0) delete reply.rewrite;
```

第二条的副作用要接受：**用户说得对但不够地道**（无 flag、有更好说法）时不会出现改写。这比出现一条假的改写安全——「更自然」的语义应该是「这里有可改之处」，不是「每句都有提升空间」。

## 七、指标修正（P1，不阻塞主线）

### 问题：`longPausePerMin` 结构性恒为 0

acf8 六轮 `longPausePerMin` 全是 0，`fillerPer100w` 也全是 0。**这不是用户表现好，是测不出来。**

whisper 会把静音吞进相邻词的时长里，所以相邻词的间隙永远是 0：

```
第 1 轮：Could=1.12s  as=1.30s  medium=1.10s   ← 全是单音节词
第 4 轮：What =1.18s
```

`words[i].start - words[i-1].end > 1.5`（`src/pipeline.ts:114`）永远命中不了。

### 替代信号

| 信号 | 判定 | 备注 |
|---|---|---|
| `wordStretch` | 单轮内时长 > 0.75s 且字符数 ≤ 5 的词数 | 会误伤句首词，需在真实数据上标定 |
| `lowConfWords` | `p < 0.62` 的实词数 | 和卡壳相关，但也可能是口音 |
| `spanRatio` | `(wav秒数) / (末词end − 首词start)` | acf8 稳定在 1.13–1.19，异常值才值得看 |

三条都**不成熟**，所以这一版的做法是：

1. 三个老指标算不出来时写 `null` 而不是 `0`
2. 新信号先只落盘、不进卡片
3. 攒够 10 场真实录音再决定卡片上放哪个

### 实现上的三个坑

**① `metrics()` 有两份，改一处没用。**

`src/pipeline.ts:103` 的 `metrics()` 和 `src/review.ts:35` 的 `aggregateMetrics()` 是同一套逻辑的两份拷贝。null 语义要改两处，还要改 `Postmortem` 类型和卡片渲染。

**② `spanRatio` 现在算不出来。**

公式要 wav 时长，但 `toWav16k()` 只回路径（`src/pipeline.ts:152`）。要么在 `toWav16k` 里顺带 ffprobe 出时长一起返回，要么这一条先不做。不写清的话它会停在「落盘」这一步落不下去。

## 八、数据与落盘 v2

```
data/
└── sessions/2026-10-26/20261026-0912-ab12/
    ├── meta.json                      # ← 恢复的唯一权威（扫盘读它）

    │   └── 001/ … 002/ …              # 正式轮次，目录号 = max+1
    └── postmortem.json
```

**不设 `threads.json`。** 上一稿打算用它做 `threadId → sessionId` 的索引，但那会变成第二份真相，和 `meta.json` 必然漂移（详见下面「重启恢复」）。要看索引就直接扫 `meta.json`——目录层级在 `data/sessions/<日>/<sessionId>/`，扫描成本可以忽略。

`meta.json` 新增字段：

```jsonc
{
  "sessionId": "20261026-0912-ab12",
  "chatId": "oc_xxx",
  "threadId": "omt_xxx",           // 话题 id，没有则 null
  "rootId": "om_xxx",              // 回复链根消息，没有则 null
  "sessionKey": "oc_xxx:omt_xxx",  // `${chatId}:${topicId}`，内部主键
  "anchorMessageId": "om_xxx",     // ← 回复用的锚点，新消息到达时更新
  "rootText": "今天去爬山了",       // ← 话题根消息正文，认不出场景时也存，用于恢复和种子
  "scenarioId": "cafe-1",          // null = 还没选场景（菜单已发、等回数字）
  "scenarioTitle": "点单，店员听错了一次",
  "seedText": null,                // ← 自由聊的种子（根消息那段话）；非 free-1 或没有种子时为 null
  "startedAt": "2026-10-26T01:12:00.000Z",
  "endedAt": null,
  "endReason": null,
  "turnCount": 0,                  // 只用于展示，不要拿它当主键
  "warmupDone": false,
  "blockUsage": { "1": "used", "2": "unused", "3": "not_reached" }
}
```

### 五个字段就是「不做状态机」的状态

§9 说「不做状态机」是对的，但要把话说全：**下面这几个字段就是状态，别在 `index.ts` 里现场发明 if-else。**

| 状态 | 判据 | bot 该做什么 |
|---|---|---|
| 根消息到达，已定场景 | `scenarioId !== null && !warmupDone` | 直接发三句卡，**跳过菜单**（§2.1） |
| 根消息到达，认不出 | `scenarioId === null && menuSent === false` | 发菜单，落 `rootText` |
| 已发菜单，未选场景 | `scenarioId === null && menuSent` | 回数字 / 短名 → 三句卡；仍认不出 → 重发菜单一句话 |
| 已选场景，未热身 | `warmupDone === false` | 等一次语音，回「重铸 + 开场」 |
| 进行中 | `endedAt === null && warmupDone` | 正常一轮 |
| 已结束 | `endedAt !== null` | 见下面 |

`menuSent` 是 `meta.json` 里要补的第 4 个字段（布尔），`seedText` 是第 5 个。没有它，「认不出根消息」和「菜单发了但用户还没回」两种情况分不开，会变成每次说话都重发菜单。

`anchorMessageId` 放进去是为了**重启后还能回对地方**——只存 `threadId` 的话，重启后拿不到能 reply 的 message_id。`rootText` 放进去是为了崩溃恢复后还能推导用户选了什么（§2.1「根消息的残留问题」）。

### `/end` 之后在同一个话题里再说话

上一稿没定义这个分支，而真实使用第二步就会撞上。**定死：已结束的话题里再发语音，回一句「这次练习结束了，开个新话题继续」，不自动重开。**

理由是别让 session 索引里一个 key 对应两个 session（目录也会撞）。想再练一次，成本就是建个话题——这和 §2「session 的边界由用户的动作定义」是一致的。

### `turnCount` 不能当轮次主键

它现在是 `src/pipeline.ts:91` 写完就不管，确实是 bug。但**修法不是「每轮更新它」**——`turnDir` 的目录名是从它推出来的（`src/pipeline.ts:142`）。写 `meta.json` 和写 `turns/001/` 之间崩掉，重启后 index 还是 1，**直接覆盖上一轮的音频和 JSON**。

正确做法：

```ts
// 下一轮 index = 扫 turns/ 目录取 max + 1（跳过 000-warmup）
const nextIndex = maxExistingTurnDir(session.dir) + 1;
```

`turnCount` 只用于卡片上显示「6 轮」，不参与任何寻址。

### 重启恢复：扫盘，不要信索引

**索引一旦独立出来就是第二份真相，必然漂移。** 崩在 `mkdir` 之后、索引写入之前，那个 session 就在盘上但谁也找不到——而它恰好是最需要被恢复的（刚开的、还没热身的）。

恢复的唯一权威是盘：

```
扫 data/sessions/*/*/meta.json → 取 endedAt === null 的 → 按 sessionKey 装回内存
```

之所以敢不设索引，是因为 agent-os 已经证明这条路可行：它把全部 session 序列化进**一个** `data/sessions.json`（`agent-os/src/core/session-store.ts`）——单一文件、`tmp + rename` 原子写、启动时 zod 校验、坏行跳过并回写、`creating`/`active` 启动时归位成 `idle`（`:25-29`）。

**本项目不需要照抄那个单文件**（我们的 session 天然散在目录里，每轮还有一堆文件），只需要照抄它那三条纪律：

1. `meta.json` 用 `tmp + rename` 原子写
2. 启动时 zod 校验，坏行跳过、不整份失败
3. 启动时把「正在跑」的状态归位，不要假设进程是干净退出的

### 两处会丢掉全部会话的小问题

**① 两条路径不一致。** `src/pipeline.ts:63` 用 `process.cwd()`，`src/lark.ts:18` 用 `import.meta.url` 推的 `REPO_ROOT`。换个目录启动，`seen-events.json` 和 `data/sessions/` 落在两个地方——扫盘恢复扫到的是空目录，已有的会话全部看不见。统一成一个（推荐都用 `REPO_ROOT`）。

**② 不是原子写。** `writeFile` 直接写整个文件，进程死在写一半就是截断的 JSON，下次启动解析失败，全部会话丢失。这一节的整个主题是抗崩溃，却用了一个抗不了崩溃的写盘方式。改成 `writeFile(tmp)` + `rename(tmp, final)`。

## 十一、本版验收

### 主脚本（cafe-1）

> 新建一个话题，第一条消息打 `1`
> → **直接**收到三句卡，不经过菜单
> → 发一条语音，用 1 号句点单
> → 收到一句语音：先确认你的句子，再说 "Hi! What can I get for you today?"
> → 第 2 轮，店员**必然**把订单听错
> → 你用 3 号句澄清
> → 发 `/end`
> → 卡片上：「三句用了两句：1 ✓ 2 ✗ 3 ✓」，「更自然」是**你自己那句话的改写**，
>    没有任何一条 flag 建立在低置信度的词上

### 副脚本（三条分支，各一条即可）

| 第一条消息 | 期望 |
|---|---|
| `hi`（认不出） | 收到菜单，**不进任何场景**；再回 `2` 能进 free-1 |
| `今天去爬山了`（一段话） | 直接进 free-1，三句卡末尾是「用英文说一句你今天干嘛了」；热身语音后 bot 的开场**接住爬山这件事** |
| 单聊里直接发语音 | 收到菜单（单聊没有「首条必须是文字」这个前提） |

### 四个容易自查踩空的地方

1. **`1 ✓` 必须来自热身轮。** 用户唯一一次用 1 号句就是热身——如果卡片上 1 号是 ✗，说明块统计没扫 `000-warmup/`
2. **整段对话里 bot 的每条消息都在同一个话题下**，没有冒出新话题
3. **时延**：从发出热身语音到听到开场语音 ≤ 5 秒（模板重铸就是为了守这条线）
4. **free-1 的卡片上没有块使用行。** 出现了 `1 ✗ 2 ✗ 3 ✗` 就是 `cardStyle` 没接上——那是在惩罚一次顺利的聊天

跑通之后再看第二件事，这个版本不问：

> **你会不会想练第 4 次。**

上一版问了但样本作废（3 次里有 2 次没启动）。这一版跑通之后重新开始数。

## 十二、跨平台：核心逻辑从飞书里抽出来

> 这一节不是这一版要做的，是**现在就把边界划对**，免得 v1.2 加小程序时重写一遍。

### 现状：耦合点比看起来少

| 层 | 现在 | 是否绑飞书 |
|---|---|---|
| ASR（`asr.ts`） | 本地 whisper，吃 wav | 否 |
| LLM（`llm.ts`） | OpenAI 兼容 HTTP | 否 |
| TTS（`tts.ts`） | MiniMax → opus | **否**（MiniMax 是独立 HTTP 服务） |
| 复盘（`review.ts`） | 纯函数，Session → 文本 | 否 |
| 轮次编排（`pipeline.ts`） | 吃 `IncomingVoice`，写盘 | **轻**：只有 `chatId` 一个字段 |
| IM（`lark.ts`） | 事件 + REST | **是** |

真正绑定的只有最后一层。`pipeline.ts` 的 `ensureSession(chatId)` 是唯一一处把「飞书的会话概念」漏进核心的地方。

### 唯一的抽象：一个接口 + 一次改名

**① 把 `IncomingVoice` 抽成平台无关的 `TurnInput`。**

```ts
export type TurnInput = {
  /** 平台内唯一的外发方 id，飞书是 chatId，小程序是 unionId，App 是 deviceId */
  peerId: string;
  /** 会话内的子上下文，飞书是 threadId/rootId，小程序是对话 id，App 同上 */
  threadKey?: string;
  /** 平台音频 blob 的本地路径。适配层负责下载 */
  audioPath: string;
  /** 平台自带的文本（语音转文字、用户输入的文字）。可空 */
  text?: string;
};

export type TurnOutput = {
  /** 要回的文字。null 表示这一轮只发语音 */
  text?: string | null;
  /** 要回的语音文件路径。适配层负责编码/上传 */
  audioPath?: string;
  /** 「正在处理」的 ack，适配层自己实现（飞书是 reaction，小程序是 loading） */
};
```

**② 平台适配层只做四件事：**

```ts
export interface PlatformAdapter {
  /** 收消息。内部负责去重、入队、ack，把平台的怪异之处全吃掉 */
  onTurn(handler: (input: TurnInput) => Promise<TurnOutput>): void;
  /** 给用户看的「一次练习」在哪里（飞书=话题，小程序=一段对话） */
  reply(output: TurnOutput, input: TurnInput): Promise<void>;
}
```

飞书版就是现在的 `lark.ts` 加一层薄包装；小程序版换成 WebSocket 或 HTTP 上传，核心一行不改。

### 为什么现在只做「改名」，不做「重构」

现在就抽接口有个真实代价：**飞书的具体怪异之处还没验完**（`group_msg` 权限、topic 的 `root_id`、语音 reply 能不能用）。抽象定得太早，会按错误的假设定错形状——比如上面 `TurnInput` 里的 `threadKey`，如果之后发现飞书的锚点必须一直带着，接口就要改。

所以这一版的做法是：

1. **只把 `chatId` 改名成 `peerId`**，`IncomingVoice` 加 `threadKey` 字段。不改包结构、不建 adapter 目录
2. `pipeline.ts` / `review.ts` **一个字都不碰飞书**（本来也没碰，除了那个字段名）
3. 等飞书这条线跑通、真要做小程序时，再按上面的接口抽——那时形状是被验证过的

**判断标准**：等到能说出「小程序和小程序之间的会话边界是什么」时再抽象。现在说不出来，先不猜。

### 三个跨平台时会撞到的东西（现在记下来）

| 问题 | 飞书 | 小程序 / App | 影响 |
|---|---|---|---|
| 音频格式 | opus，`file_key` 上传 | usually mp3 / aac，直传 | `toWav16k` 走 ffmpeg，已在，没问题 |
| 时长 | 必须填毫秒 | 不用填 | 保留 `durationMs`，平台层忽略即可 |
| 文本输入 | 文字消息也要走一遍「不是语音」的分支 | 小程序常见「发文字」 | `TurnInput.text` 已经在，不改核心 |
| 语音识别中文 | `small.en` | 同样问题 | 见 P2，与平台无关 |

结论：**核心逻辑本来就可以搬，不需要为未来做架构。需要做的是别让飞书的概念继续往 `pipeline.ts` 里长。**

### `04 §4` 那条 B 方案，在卡片上的位置

`04-教学法 §4` 选了 B 方案：「复盘第一句写『刚才我重复了你的说法，用了 really 而不是 very』」。v1.1 里它**不单独占行**——`topIssue` 的「你说 / 改 / 为什么」三行已经承担了这个作用，`为什么` 那行就是点名。

### 「对话阶段不给文字」的三处例外

这条红线保留，但 v1.1 明确三个例外，写在这里免得下轮又被当成漏洞：

1. **场景菜单**（开场前）
2. **三句卡**（场景开始前，一次性）
3. **复盘卡片**（结束后）

对话进行中**仍然一个字都不给**。热身轮也不行——热身只发语音。
