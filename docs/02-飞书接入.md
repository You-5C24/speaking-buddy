## 一、要申请的权限

| scope | 为什么需要 | 漏了会怎样 |
|---|---|---|
| `im:message` | 收消息 | 收不到事件 |
| `im:message:send_as_bot` | 发消息 | 发不出去 |
| **`im:resource`** | **下载语音资源** | **收到了事件但拿不到音频 —— 最容易漏** |
| `im:chat` | 取会话信息 | 拿不到 chat_id |
| `im:message.reaction:write` | 加 emoji 当 ack | 用户以为没收到 |

**不需要**：`docx:document`、`drive:drive`、`bitable:app`。文档和表格都砍掉了。

> ⚠️ **但「群聊相关」从 v1.1 起需要**：见 [archive/06-v1.1 §2](archive/06-v1.1-开发方案.md)。`im:message.group_msg` 是语音能在群里被收到的前提，语音没法 @ 人。

## 二、事件处理的三条硬规则

### 1. 先 ack 再干活

事件处理函数里**只做三件事**：去重 → 入队 → 加 reaction，然后立即返回。

为什么：飞书对超时未响应的事件会重推。如果你在 handler 里同步跑 ASR（2 秒）+ LLM（1.5 秒）+ TTS（1 秒），必然超时，然后**用户会收到两条一模一样的语音**。

### 2. 按 `event_id` 去重

**查和写必须一次做完**。中间隔一个 `await`，飞书重推的两条就会同时通过判断：

```ts
// 落一份最近 500 条的 seen-events.json，重启不丢
async claim(id: string): Promise<boolean> {
  await this.load();                    // ← 之后到 return 之间不能再有 await
  if (this.set.has(id)) return false;
  this.set.add(id);
  await persist();
  return true;
}
```

`if (seen.has(id)) return; ... await 别的 ...; await seen.add(id)` 是错的写法——只要有别的 await 插进来，重复推送就会同时通过。

**不是可选项。** 05 文档第 5 条就是测这个，结论是「飞书会重推」。

### 3. 按 `sessionKey` 串行，不是 `chat_id`

同一个会话同一时刻只能有一个 turn 在跑，否则两条回复会乱序到达：

```ts
const chains = new Map<string, Promise<void>>();

function enqueue(key: string, job: () => Promise<void>) {
  const prev = chains.get(key) ?? Promise.resolve();
  chains.set(key, prev.catch(() => {}).then(job));
}
```

键用 `sessionKey`（`primaryKey(msg)`，见 `src/topic.ts`）。**不要用 `chat_id`**：v1.1 一个群可以有多个话题，按 chat 串行会让 A 的 5 秒链路卡住 B，而 §9 第 11 条要的正是这个不卡。

用 `Map` 就够。不要引入 BullMQ / Redis。

## 四、语音消息的收发

### 收：下载

```
GET /open-apis/im/v1/messages/{message_id}/resources/{file_key}?type=file
```

- `type` 必须是 `file`
- 拿到的是 **Ogg Opus 容器**，直接存成 `user.opus`，不用转码
- 20 秒语音约 40–80KB

### 发：上传 + 发送，两步

```bash
# ① 转 opus
ffmpeg -i reply.mp3 -c:a libopus -b:a 24k -ac 1 reply.opus

# ② 读真实时长（毫秒，整数）
ffprobe -v error -show_entries format=duration -of csv=p=0 reply.opus
# 没有 ffprobe 时：ffmpeg -i reply.opus 2>&1 | grep Duration

# ③ 上传
POST /open-apis/im/v1/files
{ "file_type": "opus", "file_name": "reply.opus", "duration": "4320" }
# → { "file_key": "file_v3_xxx" }

# ④ 发送
POST /open-apis/im/v1/messages?receive_id_type=chat_id
{
  "receive_id": "<chat_id>",
  "msg_type": "audio",
  "content": "{\"file_key\":\"file_v3_xxx\",\"duration\":4320}"
}
```

**`duration` 填错会导致进度条错位或发送失败。** 必须读真实时长，别用字符数估算。

## 五、「正在思考」的反馈

飞书 bot 没有 typing indicator。用 reaction 代替：

```
POST /open-apis/im/v1/messages/{message_id}/reactions
{ "reaction_type": { "emoji_type": "OnIt" } }
```

用户发完语音，1 秒内在自己那条消息上看到 👀，就知道被收到了。

**这一个动作能把「等 5 秒」的体感从「卡了」变成「在处理」。** MVP 里性价比最高的一行代码。

回复发出后可以换成 ✅，也可以不管——MVP 阶段不管。

## 六、输出策略

| 时机 | 形态 |
|---|---|
| 对话中 | **只有语音** |
| TTS 挂了 | 文字兜底，并标注「语音服务异常」 |
| ASR 没听清 | 文字：「没听清，再说一次？」（不消耗轮次） |
| 结束时 | 语音（1 句收尾）+ **一张复盘卡片** |

**对话阶段绝不同时发文字。** 给了文字人就不听了。

---

## 七、结束判定（MVP 版）

只要三个来源，按优先级：

| 触发 | 判定 |
|---|---|
| 用户显式 | 发 `/end` / `/stop` / `/结束` |
| 收尾信号 | LLM 返回 `session_signal: "wrap_up"`（可选实现） |
| 硬上限 | 10 轮 |

**不做语音里的关键词判定**（"let's stop" 之类）。原文里那套「中英关键词都命中且句长 < 8 词」的规则，MVP 阶段不值得写，且容易误判。

---

## 八、故障处理

| 故障 | 处理 |
|---|---|
| ASR 空结果 | 文字「没听清，再说一次」，不消耗轮次 |
| TTS 失败 | MiniMax 失败就发文字，并标注「语音服务异常」 |
| 上传/发送失败 | 重试 3 次，仍失败发文字 |
| 管道整体超 8 秒 | 发一条文字「我这边有点慢，刚才那句收到了」 |
| 用户发图片/文件 | 忽略，回一句「我们先用语音练」 |

### 不要做的事

- **不要**在对话中提示「你刚才那句话有语法错误」——会让人闭嘴
- **不要**在等待时发「正在思考...」文字——消息流会脏，用 reaction
- **不要**结束时不打招呼——用户会以为卡死了
