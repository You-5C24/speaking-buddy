## 一、判分在哪一步做

```
对话轮 ──► 只产出 say（不判分）
/end   ──► gradeSession() 逐句判 ──► renderCard()
```

**为什么不能边聊边判**（`src/llm.ts` / `src/grading.ts` 顶部都有注释，这里说清取舍）：

| 边聊边判的问题 | 实际后果 |
|---|---|
| 同一个模型又在演角色又在打分 | 它判的是「你选了什么」，不是「你这句话对不对」。`yv5d` 第 3 轮把「你点的是茶不是咖啡」写成了语言错误 |
| 被打分挤占了注意力 | prompt 里一大段 JSON 契约，模型分给「接住这句话」的注意力变少 |
| 有 5 秒预算 | 想判准就没时间多想；想快就一定判得糙 |
| 错误会滚雪球 | 第 1 轮的错 flag 一路带到卡片上 |

拆开之后，判分不在 5 秒预算里，可以慢慢判。代价是 `/end` 要等 8–12 秒，
所以先回一句「我把这次的话过一遍，几秒」再出卡片。

## 二、四档判定

| 档 | 含义 | 谁决定 | 卡片显示 |
|---|---|---|---|
| `ok` | 语法对，母语者会这么说 | 模型 | ✓ 句子本身 |
| `unnatural` | 语法对，但没有母语者会这么说 | 模型 | ~ 句子 + 整句改写 + 为什么 |
| `wrong` | 闭集清单里的明确错误 | 模型 | ✗ 句子 + 错在哪 + 整句改写 + 为什么 |
| `unclear` | 要改的那个词是 ASR 猜的 | **代码** | ? 句子 + 「这个词没听清，这次不判」 |

### `wrong` 的闭集清单

不在清单上的问题，最多判 `unnatural`：

冠词（a/an/the，多写或漏写）· 单复数 · 动词形式（三单 -s、过去 -ed、情态后原形）·
介词 · 可数不可数（some/any、much/many）· 搭配用错 · 词性（very 修饰动词、形容词当名词用）·
疑问句语序 · 比较级最高级

**在清单上就是 `wrong`，哪怕听得懂。** `I very like this coffee` 能听懂，但 `very`
不能修饰动词，判 `✗` 不判 `~`。

### `unclear` 为什么由代码决定

模型需要一个「拿不准」的出口。给了它 `unclear`，它就会随机退过去——实测同一句
三次跑出 `ok` / `unclear` / `wrong` 三种结果。现在模型只能答三档，
`unclear` 由代码按 ASR 置信度算：

> **要改的那个词本身是猜的**，才降成 `unclear`。

关键是「要改的那个词」，不是「片段里有猜的词」：

| 句子 | 改法 | 要改的词 | 判定 |
|---|---|---|---|
| `I paid by cash` → `I paid in cash` | `by` → `in` | `by`（p=0.75，听得清） | 照常判 ✗ |
| `A regular [ice?] tea` → `iced tea` | `ice` → `iced` | `ice`（p=0.19，猜的） | `?` 不判 |

拿整个片段去查会误伤第一种：`cash` 的 p 是 0.49，但真正要改的是 `by`。

### `unclear` 不许给改法

写 `meeting → milk tea` 是在替用户猜他想说什么，正是这一档要避免的事。
代码里 `verifySentence()` 会把这个字段清掉。

## 三、稳定性：为什么每句要判三次

**kimi-k2.6 只接受 `temperature: 1`**，传 0 或 0.2 直接 HTTP 400。采样参数压不住随机性，
只能靠重复采样 + 取多数。

实测：

| 配置 | 结果 |
|---|---|
| 8 句一次判，跑两遍 | 8 句里 3 句在两档之间摇 |
| 一句一调，跑两遍 | 档位完全一致（措辞仍可能不同） |
| 一句一调 + 3 次采样投票 | 4 次跑里 3 次完全一致 |

**投票规则**（`vote()`）：过半取多数；三次全不同取**中间档**
（`ok` < `unclear` < `unnatural` < `wrong`），既不把可疑的句子判成错，也不放过明显的错。

**每句的 `agreement` 落盘**（1 = 三次全一致，0.34 = 三次全不同）。它不上卡片，
但它是判断卡片可信度的唯一依据——攒几天数据之后，先看这个分布。

### 其它三条实测约束

| 约束 | 数字 |
|---|---|
| 必须关思考 | 开着 3–4 分钟/场，关掉 8–12 秒 |
| 并发不能太高 | Moonshot 是组织级 100 RPM，3 路并发 + 429 退避重试 |
| 不加 `temperature` | 只接受 1 |

## 四、卡片

```
🎯 点单，店员听错了一次 · 7 轮
✓ 5 句没问题 · ~ 1 句不地道 · ✗ 1 句要改 · ? 1 句没听清

✓ 热身  could I get a large isomeric no

~ 第 1 轮  I want to enlarge the iced Americano.
    错在：enlarge the iced Americano → a large iced Americano
    更地道：I want a large iced Americano
    为什么：enlarge 是动词"放大"，点咖啡说大小要用 large

? 第 3 轮  A regular ice tea is better for me.
    这个词没听清，这次不判

✗ 第 5 轮  Okay, I paid by cash.
    错在：paid by cash → paid in cash
    更地道：Okay, I paid in cash
    为什么：付现金用 in cash，by cash 不是英语搭配

三句用了两句：1 ✓  2 ✓  3 —
店员第 2 轮该做的动作没做，3 号句没机会用——不是你漏了

下次先练这组
  I paid in cash. / Can I pay in cash? — 付现金用 in cash
```

### 五条硬规则

1. **每一句都点到**，不挑 3 句。没被挑中的句子，用户永远不知道自己说对了没有，
   而「我到底对不对」正是他要的答案。
2. **不给语速打分。** 用户明确说语速不重要，重要的是说得出来、说得对、说得地道。
   `wpm` 仍写进 `postmortem.json`，但不上卡片。
3. **「没问题」就只说没问题**，不加「做得很好」。「你做得很好」是最廉价的反馈。
4. **`unclear` 不是错。** 单独一档，不占过错，也不给改法。
5. **超过 14 行就把连续的 ✓ 折叠成一行**（`✓ 第 3 轮–第 7 轮 都没问题`），
   否则轮次一多就翻三屏。

### 店员该做没做的动作

`beats` 是 bot 的隐藏议程（比如「店员听错一次」）。它可能没做——`yv5d` 那场
「店员听错」一次都没发生，用户却被记成 `3 ✗`。

现在复盘会核对：听错类 beat 的换词由 `mishearTarget()` 从用户说过的话里推出，
如果 bot 那一轮的回复里没有换成那个词，就标成「店员没做，不是你漏了」，
对应的块显示 `—` 而不是 `✗`。

> 注意：**这只是如实记录，不是强制。** 店员现在仍然可能不做 beat。

## 六、对话轮不再产出 `flags` 和 `rewrite`

`Reply` schema 里这两个字段还在，**只为读回旧场次**，新的一轮不会再写。

`rewrite` 被删的直接原因：上一版有这句

```ts
if (flags.length === 0) rewrite = undefined;   // 已删除
```

语法对但不地道的句子不产生 flag，于是永远拿不到 `rewrite`——而「说得地不地道」
正好全在那一格里。现在它由评分的 `better` 字段承担。

## 七、长期指标：知道它们测不出来

`longPausePerMin` / `fillerPer100w` **结构上恒为空**，不是用户表现好：

- whisper 把静音吞进相邻词的时长，`words[i].start - words[i-1].end > 1.5` 永远命中不了
- whisper 倾向丢掉 `um` / `uh`，检测到 0 个不等于真的没说

所以这两个字段一律写 `null`，卡片显示 `—`。**`0` 表示「确实没有」，`—` 表示「测不出来」，两者不能混。**

### 替代信号（都还只落盘，不上卡片）

| 信号 | 判定 | 状态 |
|---|---|---|
| `agreement` | 三次采样一致度 | ✅ 已落盘，**先看这个** |
| 词数 / 完整句比例 | 多少轮是能独立成立的回答 | ✅ `sentences[].wordCount` / `form` |
| 块命中 | 三句卡用了几个 | ✅ `blockUsage` |
| 求助次数 | 中文或全低置信度 | ⬜ 只在 `trace.json` 里 |
| `wordStretch` | 时长 > 0.75s 且 ≤ 5 字符的词 | ⏸ 暂不做 |
| `spanRatio` | wav 秒数 / 首末词跨度 | ⏸ 暂不做，要 `toWav16k()` 回时长 |

`wordStretch` / `spanRatio` 是为绕开「静音被吞」想出来的，但**「能不能说出来」根本不用音频指标**——
词数、完整句比例、块命中、求助次数都能从转录直接算，而且实测能区分场次。
先攒数据再说。
