# 03 · 指标与复盘

这一篇是本次重写**改动最大的地方**。原文的指标体系有定义层面的错误，直接实现会得到假的进步曲线。

> ⚠️ **§二 三个指标的实现在真实数据上失效，§四 卡片模板已被 [06-v1.1-开发方案](06-v1.1-开发方案.md) §七 / §六 取代。**

## 一、原文指标的问题

### 问题 1：`errorsPer100w` 不可跨会话比较（严重）

原文把「WPM 上升且错误率不上升」定为唯一值得设的目标组合。但 `errorsPer100w` 的来源是 LLM 自报的 `flags` 数量：

```
errorsPer100w = (flags 里 type==='grammar' 的条数) / 词数 × 100
```

问题在于 **flags 的数量取决于 LLM 当时的心情**。同一句 `I very like this`，实测中 k3 给 `severity: 2`，k2.6 给 `severity: 1`，有时干脆不给。temperature 差一点、prompt 改一个字，条数就变。

**这不是一个指标，是一个噪声源。** 拿它当北极星，你会看到"退步"和"进步"大部分来自模型波动。

### 问题 2：`WPM` 的分母定义有歧义

原文：`userWords / (userSpeechMs/60000)`，「`userSpeechMs` 是用户轮次的纯语音时长」。

如果实现时取**音频文件长度**，停顿全被算进分母：

```
有 4 秒停顿的一轮：142 词 / 76 秒 = 112 wpm
无停顿的同一轮：  142 词 / 72 秒 = 118 wpm
```

结果：停顿越多，WPM 越低。**WPM 和「长停顿率」变成高度共线的两个数**，而设计把它们当两个独立信号在看。

正确做法，必须写死：

```
userSpeechMs = 首词 start → 末词 end（不是文件时长）
```

### 问题 3：`typeTokenRatio` 在小样本上是噪声

原文自己承认「词数 < 50 时不可靠」。但 142 词其实一样不可靠——单次会话 TTR 的跨轮波动远大于真实词汇进步。**直接砍掉。**

### 问题 4：「主动词汇量」名不副实

```
newActiveWords = 本次用出的词 − 历史所有会话用过的词
```

这算的是「这次说过的、以前没说过的词」，不等于「调得出来的词」。说一次不等于记住。用户会看到一个虚高的数字，然后以为自己进步了。

**MVP 不做。** 等有 10 次数据、能算「跨 3 次会话仍能复现」时再说。

## 二、MVP 只保留三个指标

全部纯声学，不依赖 LLM，不依赖跨会话状态。**这三个加起来不到 30 行代码。**

| 指标 | 算法 | 看什么 |
|---|---|---|
| `wpm` | `词数 / ((末词end − 首词start)/60000)` | 80–150 舒适区；过低是检索慢 |
| `longPausePerMin` | 相邻词间隔 > 1.5s 的次数 / 分钟 | 下降 = 流利度在涨 |
| `fillerPer100w` | `um/uh/erm/hmm` 计数 / 词数 × 100 | 过高 = 语法自动化不足 |

### 实现

```ts
function metrics(words: Word[]) {
  if (words.length < 2) return null;

  const speechMs = (words.at(-1)!.end - words[0].start) * 1000;
  const minutes = speechMs / 60000;

  let longPauses = 0;
  for (let i = 1; i < words.length; i++) {
    if ((words[i].start - words[i - 1].end) * 1000 > 1500) longPauses++;
  }

  const fillers = words.filter(w =>
    /^(um|uh|erm|hmm|er)$/i.test(w.w)).length;

  return {
    wpm: Math.round(words.length / minutes),
    longPausePerMin: +(longPauses / minutes).toFixed(1),
    fillerPer100w: +((fillers / words.length) * 100).toFixed(1),
  };
}
```

### 三个已知的局限，接受它

1. **`fillerPer100w` 只统计独立的填充词 token。** ASR 可能把 `uh` 识别成 `ah`（06 已实测到），所以**按类别合并统计，不细分到具体哪个词**。
2. **`longPausePerMin` 依赖 whisper 的时间戳精度。** 官方给的词边界有 ±50–100ms 误差，1.5s 的阈值足够宽松，不受影响。
3. **不区分「思考停顿」和「换气停顿」。** 区分需要韵律分析，第二周的事。

## 三、复盘：只挑 3 句

### 为什么不是全部

9 轮全列出来，用户只会看前两屏。原文自己在 02 里说过「一次性发完，用户只会看第一屏」，那就不该在 MVP 里做全量逐句对照。

### 挑法

```ts
function pickSentences(turns: Turn[], n = 3) {
  const scored = turns
    .filter(t => t.flags.length > 0)
    .sort((a, b) => maxSeverity(b) - maxSeverity(a));

  const picked = scored.slice(0, n);

  // 不够就补最早的两轮（有内容但没被挑中的）
  if (picked.length < n) {
    const rest = turns.filter(t => !picked.includes(t) && t.text.length > 0);
    picked.push(...rest.slice(0, n - picked.length));
  }
  return picked.sort((a, b) => a.index - b.index);
}
```

**优先 `severity 3` → 2 → 1，再按轮次补足。** 按轮次排序展示，不按严重度——按严重度展示会打乱时间线，读者对不上。

### 每句三层

```
第 5 轮
  你说：I very like this coffee
  表达：very → really（搭配问题，不是语法）
  更自然：I'm really into this coffee.
```

| 层 | 来源 | MVP 是否做 |
|---|---|---|
| 表达 | `flags[].better` + `why` | ✅ |
| 发音 | 需要音素分析 | ❌ 只给「可疑词」，见下 |
| 更自然 | LLM 同一次调用出 | ✅ |

### 发音这一层，MVP 只做「可疑词」

原设计要「movie 的 /v/ 偏 /w/」这种音素级诊断，这需要参考文本 + Azure Pronunciation Assessment，是第二周的事。

MVP 给的是**提示**而不是**判断**：

```
可疑词：latte, receipt, oat
（这些词 ASR 识别置信度低，可能是我没听清，也可能是你读得不准）
```

依据是 `words[].probability` 最低的几个实词（排除 the/a/of 这类虚词）。

> **阈值待标定，不要照抄 0.6。** 实测 `small.en` 在合成音上给出的置信度全都在 0.88 以上：

```
I     0.908
very  0.935
like  0.882
this  0.995
```

按 `< 0.6` 过滤，一个词都挑不出来。合成音太干净，这个阈值在真实带口音的录音上才有意义。

**D2 跑通后第一件事**：录一段自己的真实口语，看 `probability` 的分布落在哪，再定阈值。可能是 0.75，也可能这个信号根本不可用（那样就回到「只报指标、不挑词」，别硬凑）。

> **为什么不用 flags 挑可疑词**：原文 04 §7 想用「低置信度实词」，但又想用 `flags` 里发音相关的项。MVP 只有前者——因为 `flags` 里的 type 只有 grammar/collocation/vocab/fluency，没有发音。别为了凑数硬加一个类型。

## 四、复盘卡片模板

飞书 interactive 卡片。**一屏能看完**是硬要求。

```
【标题】 点单 · 8 轮 · 语速 112 wpm
─────────────────────────
最该改的一点
  你说：I very like this coffee
  改：  I really like this coffee
  为什么：very 不能直接修饰动词，用 really
─────────────────────────
第 2 轮
  你说：I want one latte with... um... oat milk
  更自然：Could I get an oat milk latte, please?

第 5 轮
  你说：I very like this coffee
  表达：very → really（搭配问题，不是语法）
  更自然：I'm really into this coffee.

第 7 轮
  你说：Can I have a receipt?
  更自然：Could I get a receipt, please?
─────────────────────────
今天卡住 2 次 · 长停顿 5 次 · 填充词 6.3/百词
```

### 措辞规则（很重要）

| 情况 | 措辞 |
|---|---|
| 用户主动结束 | 可以完整，3 句都给 |
| 超时结束 | **短一点，只给 1 句**。超时说明他不想练了，别再压任务 |
| 没有任何 flag | 不写「今天表现很好」，改写成「今天没有影响理解的错误」 |

**「你做得很好」是最廉价的反馈。** 没有错误就说没有错误。

## 五、`postmortem.json`

```jsonc
{
  "sessionId": "20261023-1530-ab12",
  "scenarioId": "cafe-1",
  "endReason": "user_end",          // user_end | hard_limit | idle
  "turnCount": 8,
  "durationSec": 512,

  "metrics": {
    "wpm": 112,
    "longPausePerMin": 3.9,
    "fillerPer100w": 6.3
  },

  "topIssue": {
    "said": "I very like this coffee",
    "better": "I really like this coffee",
    "why": "very 不能直接修饰动词，用 really",
    "turn": 5
  },

  "sentences": [
    {
      "turn": 2,
      "said": "I want one latte with... um... oat milk",
      "expression": "with ... oat milk 的插入略断，可以说 an oat milk latte",
      "natural": "Could I get an oat milk latte, please?",
      "audioUser": "turns/002/user.opus"
    }
  ],

  "suspiciousWords": [
    { "word": "latte", "probability": 0.41 },
    { "word": "receipt", "probability": 0.55 }
  ],

  "stalls": [
    { "turn": 5, "signal": "long_pause", "pauseMs": 4200 }
  ]
}
```

**注意 `headline` / `nextUp` 这两个字段没有了。**

原文 04 §4 的 `postmortem.json` 里有 `headline: "今天专注：把「为什么」说清楚"` 和 `nextUp: [...]`，但同时又说「复盘是攒数据不是重新推导，不再调第二次 LLM」。**这两件事矛盾**：从 9 轮 flags 里聚合出「今天专注什么」是判断，不是 concat。

MVP 的解法：**不要这两个字段。** 卡片标题直接用 `scenarioTitle` + 轮次 + wpm，这三个都是事实。

## 六、`meta.json`

```jsonc
{
  "sessionId": "20261023-1530-ab12",
  "chatId": "oc_xxx",
  "scenarioId": "cafe-1",
  "scenarioTitle": "点单",
  "startedAt": "2026-10-23T15:30:12+08:00",
  "endedAt": "2026-10-23T15:38:44+08:00",
  "endReason": "user_end",
  "turnCount": 8
}
```

**`sessionId` 里不要带 scenario。** 原文的 `20261021-1530-cafe-1-ab12` 有个问题：会话开始时用户还没选场景，ID 生成时 `scenarioId` 可能还是 null。用 `日期-时间-随机4位` 即可，场景信息只放 meta。
