## 二、LLM 选型：为什么是 `kimi-k2.7-code-highspeed`

实测了 Moonshot 的四个模型，同一个 prompt，只测延迟和 JSON 合法性：

| 模型 | 延迟（短 prompt） | reasoning tokens | 结论 |
|---|---|---|---|
| `kimi-k3` | **11.93s** | 393 | ❌ 太慢 |
| `kimi-k2.6` | **18.83s** | 802 | ❌ 太慢 |
| `kimi-k2.7-code` | 慢 | 134 | ❌ |
| **`kimi-k2.7-code-highspeed`** | **0.86 / 1.66 / 1.69s** | 72 | ✅ **选它** |

### ⚠️ 更正：上面的数字只对短 prompt 成立

写完 `src/llm.ts` 之后用**真实的 system prompt**（含规则 + JSON schema）复测：

| 场景 | 延迟 |
|---|---|
| 短 prompt（早期测试） | 0.86–1.69s |
| **真实 prompt + 3 轮对话上下文** | **1.55 / 1.67 / 1.71s** |
| **真实 prompt + 3 个不同用例（probe）** | **1.17 / 1.99 / 2.04s** |

**结论不变，但基线要改成 1.5–2.0s。** 早期那个 0.86s 是最短输入下的最好情况，不能当作设计依据。

### 另一处更正：`reasoning_tokens > 0` 不等于不能用

原文档写的判断规则是「非 0 就是推理模型，不能用于实时对话」。**这条过严。**

实测 `kimi-k2.7-code-highspeed` 每轮产生 **98–199 个 reasoning tokens**，但仍然只要 1.2–2.0 秒——因为它是「边推边出」，推理不额外阻塞。

正确的判断标准应该是 **总耗时**，不是 reasoning token 数：

| 模型 | reasoning tokens | 总耗时 | 能用吗 |
|---|---|---|---|
| `kimi-k3` | 393 | 11.93s | ❌ |
| `kimi-k2.7-code-highspeed` | 98–199 | 1.2–2.0s | ✅ |

所以 `src/llm.ts` 里遇到 reasoning tokens 只打 `console.warn`，不抛错——留证据，不拦截。

### 为什么不用 DeepSeek

`super-agent/.env` 里的 `DEEPSEEK_API_KEY` 已失效（`Authentication Fails (governor)`），且 `DEEPSEEK_MODEL` 那一行的值后面带了注释字符，直接用会拼出错误的模型名。要用得先换 key。

### 为什么不用 agent CLI（Claude Code / Cursor / Codex）

参照 agent-os 的做法：`claude -p --output-format stream-json --verbose --dangerously-skip-permissions`，续接上下文加 `--resume <session_id>`。

**实测结论：不能在在线对话链路里用。**

| 配置 | 总耗时 | TTFT |
|---|---|---|
| 首次（冷启动） | **7.68s** | — |
| 热启动 ×2 | 5.19s / 4.92s | 4.38s / 3.68s |
| `--model haiku` | 5.60s | 4.80s |
| `--model sonnet` | 5.48s | 4.67s |
| **Moonshot 直连（对照）** | **0.86–1.69s** | — |

**换轻量模型几乎没用**（haiku 5.60s vs 默认 5.19s）。延迟不在推理上，在**进程启动 + 装配工具清单 / MCP / skills / 系统提示**这一段——每个 agent CLI 都逃不掉。

按整轮算：agent 方案 ~9–10s，直连方案 ~5s。对「说完话盯着屏幕等回复」的对话场景，这是两个产品。

agent-os 能接受 5 秒，因为它是异步的（发一条指令，等结果，没人盯秒表）。口语陪练不是。

**更重要的是：这个产品不需要 agent 能力。**

| 需求 | 是否 agent 能力 |
|---|---|
| 扮演店员 / HR | ✗ 一个 system prompt |
| 每轮推进一个 beat | ✗ 一个字段 |
| 挑出 `flags` | ✗ 一次结构化输出 |
| 重铸 | ✗ prompt 里一句话 |

没有一项需要多步骤自主决策或工具调用。**这是确定性管线，不是 agent。**

### 正确的分工

```
在线（< 5s）  → 直连模型，只做对话
离线（后台）  → agent 慢慢跑：生成新场景、汇总弱项、更新复习队列
```

离线那一侧可以直接复用 agent-os 的 `spawnCli` / `ClaudeAdapter`，代码是现成的。**别把 agent 放在在线链路上。**

### 备选：Gemini 3.8 Flash（走中转站）—— 已实测，默认不启用

中转站 `https://gw.flashway.ai/v1` 提供 `gemini-3.8-flash-low / medium / high` 三档。网络不再是障碍。

**实测延迟（各 3 次，带完整 prompt + JSON 模式）**

| 模型 | TTFT | 总耗时 | reasoning tokens |
|---|---|---|---|
| `gemini-3.8-flash-low` | 3.02 / 3.16 / 3.99s | 3.2–4.4s | 未返回（≈0） |
| `gemini-3.8-flash-medium` | 4.63 / 5.50 / 5.73s | 4.9–6.2s | 266 / 283 / 380 |
| `gemini-3.8-flash-high` | 2.80 / 3.14 / 4.67s | 2.9–4.9s | 486 / 506 / 576 |

**瓶颈不是 thinking。** `high` 的 reasoning 最多，TTFT 反而最低——中转站边推边出。

**延迟来自中转站本身。** 同一个中转站，换不同家的模型测最小请求（3 token）：

| 模型 | 往返 |
|---|---|
| `gemini-3.8-flash-high` | 3.23s |
| `claude-sonnet-5-5` | 4.12 / 4.76s |
| `gemini-3.8-flash-low` | 5.10 / 5.17s |
| `gpt-6-sol` | 10.47 / 16.32s |

所有模型都慢。纯网络层对照：

```
中转站 gw.flashway.ai    connect 0.14s   ttfb 0.73–0.96s
Moonshot api.moonshot.cn connect 0.04s   ttfb 0.21–0.24s
```

中转站的 ttfb 是 Moonshot 的 3.5 倍，而这一跳只是 `/models`，还没开始推理。

**判定：不换。** TTFT 最好 2.80s，是 1.5s 线的近两倍。计入整轮：ASR 1.37 + LLM 3.2 + TTS 1 + 传输 1 ≈ **6.6s**，Moonshot 路线 ~5s。

### ⚠️ 更正：中转站上没有「真 schema」这个优势

之前判断「Gemini 的 `responseJsonSchema` 由服务端强制，能省掉重试兜底」——**在中转站上不成立**。

实测 6 次调用，**2 次**返回了 ` ```json ` 代码块包裹的内容。说明它没走 schema 强制，只是让模型「尽量输出 JSON」。

所以 `src/llm.ts` 里仍然保留 `stripFence()` + `firstJsonObject()` + zod 校验，**两个 provider 一视同仁**。这条对 Moonshot 也一样需要。

**错误分类：方向对，但一致性差**

| provider | `I very like` 判成 collocation 的比例 |
|---|---|
| Gemini（6 次） | 1/6 |
| Moonshot（4 次） | 0/4 |

两边大多数时候都判成 `grammar`，而正确答案是 `collocation`。所以 `src/llm.ts` 的 system prompt 里显式写了一条：

> `"very" modifying a verb is a COLLOCATION problem, not grammar.`

改 prompt 之后 Gemini 那次判对了。这是 **prompt 问题，不是模型能力问题**。

### 但它的响应质量确实更好

同一组用例，Gemini 的回复更像个真店员：

| 用例 | Moonshot | Gemini |
|---|---|---|
| 正确句子 | `Medium oat latte, got it. Anything else? That'll be $5.50.` | `Hot or iced for that? And can I get your name for the cup?` |

Gemini 那句更自然、更像真实对话推进。**这是它唯一确定优于 Moonshot 的地方**，但换不来 3 秒延迟。

**结论：代码里保留 adapter，默认 `LLM_PROVIDER=moonshot`。** 等中转站变快、或者要跑离线任务（场景生成、弱项汇总）时再切——那种场合 3–5 秒完全无所谓。

**判定方法（30 分钟）**

同一句话跑 5 轮，只记四个数：

| 指标 | 及格线 |
|---|---|
| **TTFT** | **< 1.5s** ← 一票否决 |
| `reasoning_tokens` | 0 或极小 |
| flags 条数一致性 | 5 次结论一致 |
| `very like` 的分类 | 应为 `collocation`，不是 `grammar` |

TTFT 过线就换。**过不了线，无论多便宜多聪明都不换。**

**成本不构成理由**

实测每轮 `prompt 105 + completion 130 = 235 tokens`。一次 10 轮练习约 2,350 tokens，任何一家都是厘级。n=1 的自用产品里，模型费用不是决策变量。

**结论：值得换，但 `llm.ts` 必须写成可替换接口。** 两家的结构化输出 API 形状完全不同（一个只要 `response_format`，一个要 `responseMimeType` + `schema`），不抽象的话换模型等于重写。

### JSON 输出的实际表现

开 `response_format: {"type": "json_object"}` 后，两个模型都能稳定吐出合法 JSON。k3 的那次甚至把完整推理过程放在 `reasoning_content` 里、`content` 保持纯 JSON —— 所以**解析必须只取 `content`，不能取整个 message**。

仍然要 zod 校验。理由不是「模型会出错」，而是「出错时要有个明确的分支」：

```
JSON.parse → zod.parse → 失败则带上错误重试一次 → 仍失败则发固定兜底句并记 trace
```

没有兜底路径的 JSON 契约，第一次异常就会让整个会话卡死。

## 三、ASR：唯一有坑的一项

### 排除的方案

| 方案 | 为什么不行 |
|---|---|
| SiliconFlow Qwen3-ASR | 余额 0（`code: 30001 account balance is insufficient`） |
| `brew install whisper.cpp` | 失败：`raw.githubusercontent.com` 连接被重置，拉不到 formula。formula 已改名为 `whisper.cpp`，但改名不解决网络问题 |
| `git clone` whisper.cpp | 超时 |
| `@huggingface/transformers` | `onnxruntime-node` 要求 macOS 14，本机 13.5.1，`dlopen` 报 `built for macOS 14.0 which is newer than running OS`。切 `device: 'wasm'` 也没用，它仍会先加载 node binding |
| faster-whisper 默认装 | 失败：`av` 16.x 只有 `macosx_14_0` wheel，退化成源码编译，卡在 `pkg-config is required for building PyAV` |

### 可行方案：faster-whisper + 固定 av 版本

```bash
python3 -m venv .venv
.venv/bin/pip install --prefer-binary \
  -i https://mirrors.aliyun.com/pypi/simple/ \
  --trusted-host mirrors.aliyun.com \
  "av==15.1.0" faster-whisper
```

**关键在于 `av==15.1.0`。** 它是最后一个提供 `macosx_13_0_arm64` wheel 的版本：

| av 版本 | 提供的 wheel 标签 |
|---|---|
| 13.1.0 – 14.1.0 | `macosx_11_0_arm64` |
| **15.0.0 – 15.1.0** | **`macosx_13_0_arm64`** ← 匹配本机 |
| 16.0.0+ | `macosx_14_0_arm64` ← 装不了 |

其余依赖都没问题：`ctranslate2 4.8.3` 是 `macosx_11_0_arm64`，`tokenizers` 也是 `macosx_11_0`。

### 网络前提

- `HF_ENDPOINT=https://hf-mirror.com` —— 模型从 HuggingFace 镜像下，官方站点不可达
- pip 必须走镜像 —— 本机 python3 的 CA 证书有已知问题，会报 `SSLEOFError`

### 模型大小

M1 Pro / 16GB：

| 模型 | 大小 | 适合 |
|---|---|---|
| `base.en` | ~145MB | 够快，但非母语口音下错得多 |
| **`small.en`** | **~480MB** | **推荐**，`int8` 下 10s 音频约 1–2s |
| `medium.en` | ~1.5GB | 准确率更好，但延迟吃紧 |

`compute_type="int8"` + `device="cpu"`。M1 的 Metal 对 ctranslate2 支持有限，别花时间折腾。

### 为什么一定要本地

不是省钱，是**要词级时间戳**。06 已实测三个云端 ASR 都只返回 `{text, duration, language}`，没有 `words[]`。而：

- 长停顿检测 → 需要词的 start/end
- 卡壳点识别 → 需要词的 start/end
- 可疑词挑选 → 需要词的 confidence

**没有时间戳，产品就退化成"带总结的聊天机器人"**，卡壳点这个最有价值的指标直接消失。

## 四、TTS：为什么换成 MiniMax

原先选的是 `msedge-tts`（免费、无 key）。它走的是 Edge 浏览器朗读接口，不是正式 API。2026-10-25 在本机实测已经挂了：

| 地址 | 结果 |
|---|---|
| `wss://api.msedgeservices.com/tts/cognitiveservices/websocket/v1` | HTTP 200，空 body，连接没有升级成 WebSocket |
| `wss://speech.platform.bing.com/.../edge/v1` | 连接被重置 |

语音识别和 LLM 那一轮是通的，停在合成。所以当前 TTS 改成 MiniMax 同步接口。Azure 仍然放到第二周，和发音评估一起做。

| 方案 | 状态 | 说明 |
|---|---|---|
| msedge-tts | ❌ 本机不可用 | 2026-10-25 起握手失败，不再作为出链路 |
| **MiniMax `t2a_v2`** | ✅ **当前** | `POST https://api.minimax.cn/v1/t2a_v2`。`speech-2.8-hd` + `English_Gentle-voiced_man`，语速 1.0 |
| Azure Speech | ❌ 暂缓 | 第二周接发音评估时一起搞 |

```ts
await fetch("https://api.minimax.cn/v1/t2a_v2", {
  method: "POST",
  headers: { Authorization: `Bearer ${process.env.MINIMAX_API_KEY}` },
  body: JSON.stringify({
    model: "speech-2.8-hd",
    text,
    stream: false,
    output_format: "hex",
    voice_setting: { voice_id: "English_Gentle-voiced_man", speed: 1 },
    audio_setting: { sample_rate: 32000, bitrate: 128000, format: "mp3", channel: 1 },
  }),
});
```

返回的 `data.audio` 是 hex mp3。之后仍用 ffmpeg 转 opus，再用 ffprobe 读真实毫秒数发给飞书。

### 还要记住的

1. **Key 放 `.env` 的 `MINIMAX_API_KEY`。** 在 [MiniMax 开放平台](https://platform.minimax.cn/) 的「账户管理 → 接口密钥」创建。账户没余额会直接拒。
2. **模型用 `speech-2.8-hd`。** 短句要语气，不用 turbo。
3. **音色用 `English_Gentle-voiced_man`。** 这把 key 上的英文系统音色只有 6 个，这是通用美式口音。`English_Graceful_Lady` 是英式朗诵腔，不用。音色写在 `config/scenario.json` 的 `voice`，不填则用 `MINIMAX_VOICE`。
4. **默认语速 1.0。** 某个场景要放慢时再写 `ttsRate: "-10%"`，由 `tts.ts` 换成 MiniMax 的 `speed`。
5. **MiniMax 失败就发文字**，并标明语音服务异常。没有第二家 TTS 再兜一层。

## 五、ffmpeg / ffprobe

### 用 npm 的静态二进制，别 brew

```bash
pnpm add ffmpeg-static ffprobe-static
```

`ffmpeg-static` 只有 ffmpeg，**不含 ffprobe** —— 这就是 06 文档里「本机完全没有 ffprobe」那个坑的根因。两个包分开装。

### 两个反直觉的事实（已实测）

**1. `-ar 16000` 对 opus 是无效的。**

```bash
ffmpeg -i in.mp3 -c:a libopus -b:a 24k -ar 16000 -ac 1 out.opus
# 结果：Stream #0:0: Audio: opus, 48000 Hz, mono
```

libopus 内部固定 48kHz，ffmpeg 静默忽略 `-ar`。这是正常的，不用修，也不用担心文件变大——码率是由 `-b:a` 决定的，实测 5.36s → 14KB。

**2. 不装 ffprobe 也能读时长。**

```bash
ffmpeg -i out.opus 2>&1 | grep Duration
# Duration: 00:00:05.36, start: 0.000000, bitrate: 21 kb/s
```

解析 `Duration:` 行即可。装上 `ffprobe-static` 更省事（`-show_entries format=duration` 输出干净），但这条退路要记住——否则会像 06 里那样，误以为「没有 ffprobe 就发不了语音」，白卡一天。

### 转码参数

| 用途 | 命令 |
|---|---|
| 入链路（给 ASR） | `ffmpeg -i in.opus -ar 16000 -ac 1 -c:a pcm_s16le out.wav` |
| 出链路（给飞书） | `ffmpeg -i in.mp3 -c:a libopus -b:a 24k -ac 1 out.opus` |

入链路必须 16k（whisper 要求），出链路 48k 也没关系。

## 六、飞书

### 接入方式

`@larksuiteoapi/node-sdk` 的 `WSClient`，**不要写 HTTP webhook**。好处是不需要公网 IP、不需要配回调地址、不用处理签名校验。

```ts
const wsClient = new Lark.WSClient({ appId, appSecret });
wsClient.start({ eventDispatcher: dispatcher });
```

照抄 `agent-os/src/im/lark.ts:407`。

### 凭据在哪

`../super-agent/.env` 里有 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`。用同一个自建应用还是新建一个都行，权限见 [02-飞书接入](02-飞书接入.md)。

### 三个必踩的坑

1. **语音消息没有下载 URL。** content 是 `{"file_key":"...","duration":3000}`，必须再调一次资源接口，且 `type` 必须是 `file` —— 传 `image` 拿不到。
2. **发语音要自己算 `duration`，单位毫秒。** 填错进度条错位，甚至发不出去。
3. **飞书 bot 没有 typing indicator。** 用 reaction（`OnIt` 表情）代替，1 秒内让用户知道被收到了。

## 七、明确不引入的东西

| 不引入 | 理由 |
|---|---|
| Express / Nest | WS 长连接不需要 HTTP 服务 |
| Prisma / SQLite | JSON 够，且能直接 `git diff` |
| Redis / BullMQ | 单用户，一个 `Map<chatId, Promise>` 就够串行 |
| Docker | 自用，跑在本机 |
| LangChain / Agent SDK | 这是确定性管线不是 agent。套 agent 框架只会增加延迟和不可预测性 |
| TypeScript 构建（tsc/tsup） | `tsx watch` 直接跑 TS |
