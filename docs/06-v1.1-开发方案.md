# 06 · v1.1 开发方案

**这一版只做三件事**：一次练习 = 一个话题；开口前给三句卡并强制热身；场景可挑，另加自由聊。

不改技术栈，不改 ASR/TTS/LLM 选型，不引入新依赖。前半部分全是在接已经存在但没接上的线。

## 一、这一版的依据：acf8 那 6 轮暴露的问题

三个体感对应四个可复现的缺陷。每个都有数据和行号，不是猜测。

| # | 缺陷 | 证据 | 影响 |
|---|---|---|---|
| 1 | **开场白从来没说过** | `scenario.opening` 只作为 assistant 历史塞进 prompt（`src/llm.ts:82`），从未走 TTS。`src/index.ts:104` 的注释写着「用户已经听到」 | 用户不知道场景开始了 |
| 2 | **`beats` 没进 prompt** | `src/pipeline.ts:184-185` 只传 `persona` 和 `opening`，`level` / `goal` / `beats` 全部丢弃 | 场景唯一的教学机制（店员听错）一次没发生 |
| 3 | **低置信度的词照样产生 flag** | `as` p=0.523 时长 1.30s → 被判「多余」；`pay` p=0.38 → `main` 被改成 `mean`。`p` 从未进过 prompt | 用户在挨纠正一个没犯过的错 |
| 4 | **`natural` 填的是 bot 自己的台词** | `src/review.ts:131` `natural: t.reply.say` | 卡片上写「你说：No. → 更自然：Got it. That's $3.25」——那不是你的话的更好版本 |

### 缺陷 1 的两个直接后果

`20261025-1206-srty`：用户说的是 **"Hi, what can I get for you today?"** ——他在演店员。因为对话框一声不响，他不知道谁该开口。
`20261025-1148-a5ps`：用户说的是文档里的测试句 **"I very like this coffee"**，一轮就没了。

**这两次不算「练了 3 次」，算 1 次真练 + 2 次没启动。** 想验证「会不会练第 4 次」，得先把这 3 次变成真的 3 次。

### 缺陷 2 的直接后果

acf8 六轮里，用户一共说了 **21 个词**，其中 4 轮 ≤ 4 词：

```
1  Could I get a medium as Americano?   (7)
2  No.                                  (1)
3  Tom                                  (1)
4  What is the main pay at the register? (8)
5  Cash, please.                        (2)
6  Okay, here we go.                    (4)
```

bot 说的话比用户多。根子不是水平不够，是**bot 问的问题一个词就能答完**：`Anything else? → No.`

而设计上本来用来逼整句的装置（店员听错 → 用户必须澄清）没接线。第 3 轮和第 6 轮还都在说「一会儿叫你」——因为没有任何场景状态，剧情在原地打转。

## 二、交互模型：群 → 话题 → 一次练习

用户建群、建话题，bot 不建。这样 session 的边界由用户的动作定义，最不会歧义。

```
群：「口语练习」（话题群）
 ├── 话题「点单 · 10-25 12:25」
 │     ├─ 菜单（文字）
 │     ├─ 三句卡（文字）
 │     ├─ 热身轮（你 1 条语音 / bot 1 条语音）
 │     ├─ 开场语音 "Hi! What can I get for you today?"
 │     ├─ … N 轮 …
 │     └─ 复盘卡片
 └── 话题「自由聊 · 10-26 08:10」
       └─ …
```

### session 的键

```ts
const sessionKey = message.thread_id ?? message.chat_id;
```

- **话题群**：`thread_id` 一定有 → 每个话题独立
- **普通群 / 单聊**：没有 `thread_id` → 退回 `chat_id`，退化成「一个对话框一场长会话」
- 群名、话题名只给人看，**程序只看 id**。别去匹配标题

回复必须**落回同一个话题**，否则长对话会跑进群的主消息流：

```ts
// 二选一，先试后者
client.im.v1.message.reply({ path: { message_id }, data: { msg_type, content, reply_in_thread: true } })
// 或
client.im.v1.message.create({ params: { receive_id_type: 'thread_id' }, data: { receive_id: threadId, ... } })
```

### 触发时机

| 场景 | bot 动作 |
|---|---|
| 被拉进群（`im.chat.member.bot.added_v1`） | 发一句说明：「建一个话题就是一次练习。在话题里发语音开始。」 |
| 某个话题第一次收到消息 | 发**场景菜单**（文字） |
| 菜单里选完 | 发**三句卡** + 等热身 |
| 热身轮说完 | 确认 + 开场语音 → 正式进入场景 |
| `/end` | 复盘卡片 |

**菜单不发卡片，用纯文字。** 手机上回一个数字比点按钮快，且不需要开 `card.action.trigger` 回调。

```
这次练什么？

1  点单 · 店员会听错一次          A2
2  退货 · 你忘带小票了            A2
3  自由聊 · 随便说，我接住

回数字。直接发语音 = 从 1 开始。
```

### 权限与阻塞

> 🔴 **动手第一天先验这一条，不通就得改方案。**

飞书 bot 在群里默认**只收到 @ 自己的消息**（`im:message.group_at_msg` 级别的权限）。而**语音消息没法 @ 人** —— 所以群里发语音，bot 一条都收不到。

必须在开发者后台把权限放到「接收群内全部消息」（`im:message.group_msg`，后台实际名称以页面为准），并且把 `src/lark.ts:210` 那行 `chat_type !== 'p2p'` 的过滤改掉。

验证动作：
1. 建话题群，拉 bot 进去
2. 在话题里发一条纯语音（不 @）
3. 确认事件到达，且 `message.thread_id` 非空、`chat_type === 'group'`、`chat_mode === 'topic'`

三条都成立才能按本文档的模型做。`thread_id` 拿不到，就退回「一个群一场练习」，其余设计不变。

## 三、练前预习：三句卡 + 强制热身

这是这一版最核心的功能。对应教学法上的 **TBLT pre-task**（Willis 三段式的第一段）和 Ellis 的 pre-task planning 研究：开口前给 2–3 分钟准备，输出的复杂度、准确度、流利度都会上升。

你现在的处境是「零准备 + 必须临场组句」，研究里这是最差的组合。

### 卡的形态

```
━━━ 点单 · 店员会听错一次 ━━━
今天用这三句，别的不会说也没关系：

1  Could I get a ___ ?
   Could I get a medium latte?
   也可以换：medium Americano / large iced coffee / oat milk latte

2  For here, please.
   或者：To go, please.

3  Sorry, I meant ___ .
   Sorry, I meant oat milk, not soy.

准备好了发一条语音，先用 1 号句造一句。
```

### 颗粒度：整句 + 一个槽

三种颗粒度里选中间那个：

| 形态 | 例子 | 问题 |
|---|---|---|
| 词 | `coffee` | 你已经会了，没有价值 |
| **块 + 槽** | `Could I get a ___ ?` | **选它**：有整句兜底，又有槽位逼你换词 |
| 整句 | `Could I get a medium latte, please?` | 只能照念，检索量最小 |

「组句」的最小可行版本不是从零件搭句子，是**换一个零件**。对 A2 这已经够难，而且不会把你打回沉默。

### 强制热身（不可跳过）

热身不是可选步骤，是**这一步必然发生**：

```
① 你发一条语音，用 1 号句造一句
② bot 回：Nice, a medium latte. Okay — Hi! What can I get for you today?
   （前半句是重铸，后半句是开场。合成一个轮次，不额外多一轮）
```

这一步的价值：**把最难开口的第一句挪到无风险状态**。人第一次开口的心理门槛，比后面九轮加起来都高。

约束：
- 热身轮单独落 `turns/000-warmup/`，**不计入正式轮次**
- 你在热身里说了别的话（没用 1 号句），**也照常进入场景**，不重来、不提示、不卡住。只在复盘记一笔
- 「不可跳过」指的是这个步骤存在、bot 等你这一个语音轮次；不是指拒绝前进

### 复盘验收：防短语本

卡片上多一行：

```
三句用了两句：1 ✓  2 ✗  3 ✓
```

这是整件事的**闭合机制**。没有它，三句卡只是一张传单；有了它，块和任务之间形成回路。

实现很便宜：拿当轮 ASR 文本做小写子串匹配，场景配置里每块带一个 `match` 数组。

```ts
match: ['could i get', 'can i get', "i'd like", "i'll have"]
```

**允许误判。** 这是个提醒，不是考试；不做分数（04 §1 红线）。

### 选块标准：三条，缺一不收

1. **这个任务里我一定得说它** —— 否则是短语本
2. **换个话题我就不说了** —— 否则是通用句型库（04 §1 红线）
3. **说了对方一定听懂** —— 不靠语调、不靠连读

按这三条筛，**`I'm kinda ...` 进不了 A2 第一批**。它是语用上的模糊限制词（hedging），作用是让语气松一点，属于「听着像母语者」的装饰，不是「把想说的说出来」的工具。而且 `kinda` 的发音没到位，说出来更像含糊。

`I'm gonna ...` 频率极高，但**点单任务里用不上**——它属于自由聊的卡，不属于点单的卡。这正好印证「每场景一小组」，不是全局句型库。

## 四、场景配置 v2

`config/scenarios/` 一个场景一个文件，`index.json` 列目录。不再有单例缓存。

```jsonc
// config/scenarios/cafe-1.json
{
  "id": "cafe-1",
  "title": "点单，店员听错了一次",
  "level": "A2",
  "goal": "点一杯咖啡，并在店员听错后用一句澄清",
  "persona": "a friendly but brisk barista at a coffee shop. You are mid-shift, the queue is long, and you speak in short sentences.",
  "opening": "Hi! What can I get for you today?",
  "voice": "English_Gentle-voiced_man",

  "blocks": [
    {
      "n": 1,
      "frame": "Could I get a ___ ?",
      "example": "Could I get a medium latte?",
      "swaps": ["medium Americano", "large iced coffee", "oat milk latte"],
      "match": ["could i get", "can i get", "i'd like", "i'll have"]
    },
    {
      "n": 2,
      "frame": "For here, please.",
      "example": "For here, please.",
      "swaps": ["To go, please."],
      "match": ["for here", "to go"]
    },
    {
      "n": 3,
      "frame": "Sorry, I meant ___ .",
      "example": "Sorry, I meant oat milk, not soy.",
      "swaps": ["Sorry, I meant a medium.", "Sorry, I meant iced."],
      "match": ["i meant", "i mean", "sorry, i wanted"]
    }
  ],

  "beats": [
    {
      "atTurn": 2,
      "need": "店员听错一次，用户澄清（且只发生一次）",
      "directive": "This turn, mishear one detail of their order — swap the milk, the size, or the temperature. Say the wrong version back as if you were writing it down. Do not apologize yet."
    },
    {
      "atTurn": 4,
      "need": "确认在这里喝还是带走",
      "directive": "Ask whether it's for here or to go."
    }
  ]
}
```

### beat 由代码注入，不靠模型自觉

```ts
const beat = scenario.beats.find(b => b.atTurn === turnIndex);
// beat 存在时，在 system prompt 末尾追加一段
if (beat) system += `\n\nTHIS TURN ONLY: ${beat.directive}`;
```

**为什么不用状态机、也不让模型自己推进**：「店员听错一次」如果只是 prompt 里的一句软要求，它会在某轮悄悄消失——acf8 就是一次都没发生。按轮号注入是确定性的，代价只有几行。

`atTurn` 用固定轮号而不是「满足条件才触发」，是因为用户不一定按剧本走（第 2 轮可能只说了 `No.`）。第 2 轮说什么都会被听错，这本来就是真实店员的行为。

### 自由聊：`free-1`

```jsonc
{
  "id": "free-1",
  "title": "自由聊",
  "level": "A2",
  "persona": "a patient friend who is genuinely curious. You speak plainly and never lecture.",
  "opening": "Hey. What's been going on today?",
  "blocks": [
    { "n": 1, "frame": "How do you say ___ in English?", "match": ["how do you say"] },
    { "n": 2, "frame": "What's another word for ___ ?", "match": ["another word for"] },
    { "n": 3, "frame": "Sorry, can you say that again?", "match": ["say that again", "repeat that"] }
  ],
  "beats": []
}
```

自由聊的三句卡不教话题词汇，教**求助用的元语言**。理由是：自由聊里你卡住的时刻全是「这个词我不会说」，而这句卡就是那时的出口。

> ⚠️ 这三句只能解决一半。真到「拿铁怎么说」的时候你还会蹦中文，而 `small.en` 会把中文硬转成乱码英文。见 [§10 P2](#p2-可以这一版不做)。

自由聊**不设 goal、不设 beats**，但仍然记 `flags`、仍然出复盘。不逼目标，不等于不记录。

## 五、Prompt 变更

`src/llm.ts` 的 `RULES` 追加三条，其余不动：

```
- The learner is A2. Prefer questions they can answer in one full sentence:
  yes/no questions with a reason, A-or-B choices, "what kind of ___".
  Never ask an open question that can be answered with one word.
- Never ask "Anything else?" as your only question. It invites a one-word answer.
- If a word appears in "ASR was unsure about" below, do NOT build a flag on it.
  Drop the flag instead of guessing.
```

并在 `buildMessages` 里带上：

```ts
system += `\n\nScenario goal: ${goal}`;
system += `\n\nBlocks the learner prepared (they may use these):\n` +
  blocks.map(b => `${b.n}. ${b.frame}`).join('\n');
```

### 置信度护栏

把 ASR 的低置信度**实词**列给模型：

```ts
const unsure = words
  .filter(w => w.p < 0.62 && w.w.replace(/\W/g, '').length > 1)
  .filter(w => !STOPWORDS.has(w.w.toLowerCase().replace(/\W/g, '')))
  .map(w => `"${w.w}" (${w.p})`);
if (unsure.length) system += `\n\nASR was unsure about: ${unsure.join(', ')}`;
```

阈值 0.62 的依据是 acf8 的真实分布：

| 词 | p | 真值 |
|---|---|---|
| `pay` | 0.38 | 幻觉（用户说的是 mean） |
| `Cash,` | 0.41 | 真词，但被拉长 |
| `Americano?` | 0.46 | 真词 |
| `as` | 0.52 | 幻觉 |
| `Okay,` | 0.51 | 真词 |
| `medium` | 0.94 | 真词 |

低置信度 ≠ 幻觉，所以**不是直接丢词，是禁止在它上面建 flag**。模型仍然看得见完整转录。

### 新增输出字段 `rewrite`

```ts
export const Reply = z.object({
  say: z.string().min(1).max(300),
  /** 用户这句话，母语者会怎么说。和原句一样就省略 */
  rewrite: z.string().max(200).optional(),
  flags: z.array(Flag).max(5),
});
```

prompt 里：

```
- "rewrite": if the learner's sentence could be said more naturally, write THEIR
  sentence the way a native speaker would. Same meaning, same length roughly.
  Not your own reply. Omit if nothing to improve.
```

这一条修缺陷 4。复盘卡片的「更自然」从此取 `rewrite`，**永远不用 `reply.say`**。

## 六、复盘卡片 v2

```

─────────────

## 七、指标修正（P1，不阻塞主线）

### 问题：`longPausePerMin` 结构性恒为 0

acf8 六轮 `longPausePerMin` 全是 0，`fillerPer100w` 也全是 0。**这不是用户表现好，是测不出来。**

whisper 会把静音吞进相邻词的时长里，所以相邻词的间隙永远是 0：

```
第 1 轮：Could=1.12s  as=1.30s  medium=1.10s   ← 全是单音节词
第 4 轮：What =1.18s
```

`words[i].start - words[i-1].end > 1.5`（`src/pipeline.ts:114`）永远命中不了。

### 替代信号

| 信号 | 判定 | 备注 |
|---|---|---|
| `wordStretch` | 单轮内时长 > 0.75s 且字符数 ≤ 5 的词数 | 会误伤句首词，需在真实数据上标定 |
| `lowConfWords` | `p < 0.62` 的实词数 | 和卡壳相关，但也可能是口音 |
| `spanRatio` | `(wav秒数) / (末词end − 首词start)` | acf8 稳定在 1.13–1.19，异常值才值得看 |

三条都**不成熟**，所以这一版的做法是：

1. 三个老指标算不出来时写 `null` 而不是 `0`
2. 新信号先只落盘、不进卡片
3. 攒够 10 场真实录音再决定卡片上放哪个

### 填充词的已知局限

whisper 倾向于**丢掉** `um` / `uh`。acf8 六轮检测到 0 个填充词，很可能不是真的没有。写进文档当已知事实，别再拿它当「你表现不错」的证据。

```

**`turnCount` 永远是 0 是个已存在的 bug**（`src/pipeline.ts:80` 写完就不管了）。v1.1 里它决定恢复和复盘，必须每轮更新。

**重启恢复**：进程启动时读 `threads.json`，把未结束的 session 从盘上还原进内存，包括轮次上下文。现在「崩了重发一句就行」的假设在群模型下不成立——群和话题还在，用户会接着说话，而 bot 已经不记得在练什么了。

## 十、动手前必须验的两条

> 这两条是阻塞项。不通就得改方案，别先写代码。

### 1. 🔴 群消息能不能收到（含语音）

见 [§2 权限与阻塞](#权限与阻塞)。要点：语音消息不能 @ bot，必须拿到「接收群内全部消息」的权限。

**退化路径**：拿不到权限 → 改成「一个群一场练习」，用户在群里发语音时不 @（仍然不通），或退回单聊 + 手动 `/new` 切场。**先验再设计。**

### 2. 🔴 `thread_id` 在话题群里是不是稳定存在

| 检查 | 期望 |
|---|---|
| 话题内发语音，事件里 `message.thread_id` | 非空 |
| `message.chat_type` | `group` |
| 群信息里 `chat_mode` | `topic` |
| 回 `reply_in_thread: true` 后消息落在哪 | 同话题，不进主消息流 |

`thread_id` 拿不到 → 退回 `chat_id` 分场（一个群一场），三句卡和热身的设计完全不受影响。

## 十一、本版验收

一条完整脚本，跑通就算这一版成立：

> 新建一个话题，发一句「hi」
> → 收到场景菜单
> → 回 `1`
> → 收到三句卡（3 个块，每个带槽和替换）
> → 发一条语音，用 1 号句点单
> → 收到一句语音：先确认你的句子，再说 "Hi! What can I get for you today?"
> → 第 2 轮，店员**必然**把订单听错
> → 你用 3 号句澄清
> → 发 `/end`
> → 卡片上：「三句用了两句：1 ✓ 2 ✗ 3 ✓」，「更自然」是**你自己那句话的改写**，
>    没有任何一条 flag 建立在低置信度的词上

跑通之后再看第二件事，这个版本不问：

> **你会不会想练第 4 次。**

上一版问了但样本作废（3 次里有 2 次没启动）。这一版跑通之后重新开始数。
